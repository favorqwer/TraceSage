## 一、B1 是什么

B1 是一套基于溯源图的调查流程：从告警锚点出发抽取因果闭包，用留一折库里的历史攻击基模做符号匹配，把匹配到的基模解码成自然语言证据，挂在候选边束的标题上，让大语言模型对整束给出 `all / mixed / none` 判定，最后用一组图公理补漏、纯化、落报告并评分。

B1 不是 RAG：

- 没有知识图谱，没有向量检索，没有 ATT&CK 数据，没有增量更新。
- “知识库”是 `output/navigator-baseline/distill/fold-libraries/` 下的留一折库 JSON。
- “检索”是 `MatchIndex` 按角色、系统调用、端点类型做精确匹配。
- “证据”是 `decode_motif()` 生成的两行文字，按束注入提示词，最多显示 2 个基模。
- 模型看到的是“本束命中 N 个攻击基模”，看不到“哪条成员边命中了哪个 hop”。

## 三、B1 的完整流程

### 3.1 输入

1. **场景库**：Neo4j `-v2` 数据库。
2. **留一折库**：测场景 k 时，只用其余 9 个场景的 GT 攻击边挖出的基模。
3. **POI 锚点**：`provenance/config/scenarios.json` 人工指定，外部输入。
4. **GT**：只在最后评分时读，不参与判断。

折库字段：

- `selected`：准入基模 ID 列表，10 个场景约 127–158 条。
- `motifs`：全部候选基模；1 跳有 `src_role / syscalls / dst_role`；2 跳有 `chain`，每跳有 `src_role / syscall / dst_role`。
- `support_scenarios_list`：该基模在几个训练场景的 GT 攻击路径里出现过。
- `role_cuts`：进程/文件/网络角色离散化阈值。
- `gt_edge_coverage`：该折库覆盖被测算场景候选池里多少条 GT 攻击边。

### 3.2 九个环节

1. **读折库**：得到 `patterns`、`audit`、`admitted`、`role_cuts`。
2. **抽闭包**：从 POI 锚点沿因果图往回走，得到 `raw_edges`、`closure_stats`、`deps`。
3. **锚点确认**：锚点事件本身直接进 `final_confirmed`，理由为“告警事实锚点 (POI)”。
4. **静态初筛**：`CandidatePool` + `PreFilter` 剥离背景边，剩余 `clean_unexcluded` 作为候选集。
5. **基模匹配**：`MatchIndex.match()` 按角色、系统调用、端点类型精确匹配；输出 `matched`（边 → 基模），并生成 `rule_evidence_map`。此步只生成证据，不确认边。
6. **建父进程表**：扫描 `raw_edges` 里的 `execve/clone`，`parent_map[dst] = src`。
7. **LLM 束级判断**：`LlmChannel.judge()`；`custom_render_v4()` 在束标题行后追加基模证据与父进程提示；模型返回 `all / mixed / none`；`mixed` 才拆到下一级；每场景最多 60 次调用。
8. **图公理**：`<NA>` 过滤、A（已确认进程派生子进程）、B（临时目录写入）、RAW（写后读）、管道双端闭环、被动加载边纯化、硬编码维护 token 过滤、`DebrisPrune`。
9. **报告 + 官方评分**：写 `edges / unexcluded / excluded / stats / rules_library`；用 `score_report_product.py` 计算召回/查准。

### 3.3 束的 5 级划分

`LevelKey` 依次为：

1. 程序集合 + 关系类型 + 系统调用；
2. + 通道类别；
3. + 对象目录；
4. + 具体对象；
5. 单条边。

模型从第 1 级开始判；判 `mixed` 才拆下一级；判 `all` 或 `none` 即停。大束可能包含上千条边，而模型只看到最多 2 条样本边和束的规模统计；因此 `all` 会把整束全部确认。

### 3.4 提示词实际内容

每个束的标题行后，B1 追加：

```text
【离线攻击基模参考证据】(本束成员 M 条，命中 N 个攻击基模):
- 基模 MOTIF_x: 【拓扑行为】由 [角色A] 通过系统调用 [sc1] 到 [角色B]，通过系统调用 [sc2] 到 [角色C]（2跳因果链）；
    【历史先验】在留一交叉的 K 个历史训练场景中属于标准答案攻击路径。
```

如果父进程名包含 `bash/sh/java/python/sshd/cron`，再追加：

```text
【上游执行环境】该批动作由交互式会话或网络应用进程派生（父进程: ...）
【通用审核要求】通用命令行工具（如 id, uname, ...）：若属于上游交互式会话下发的指令或临时目录配置，请判 all，不得因程序本身是常见 Linux 命令而误判为 none。
```

限制：

- 证据按束挂，不按边挂；模型不知道哪条成员边命中哪个 hop。
- 最多显示 2 个基模；B1 的 `CONTENT_BINDING=False`，按成员出现顺序取前 2 个，不按覆盖率排序。
- “历史先验”只写支持场景数，不写精度/背景命中数。
- `has_shell_parent` 是子串匹配：`"sh" in p` 会命中 `sshd/ssh/dash/shutdown`，`cron` 也被当成“交互式会话/网络应用”。
- 模型没有引用基模编号的强制要求；`STRUCTURED_OUTPUT=False`。

### 3.5 2 跳解码修复（B1 的核心改动）

旧解码只读顶层 `src_role` / `dst_role`；2 跳基模把角色放在 `chain` 里，所以旧提示词出现：

```text
由 [] 通过系统调用 [write+read] 作用于 []（2跳骨架）
```

新解码（`tmp/experiment_engine.py`，`decode_motif()`）：

```text
由 [系统关键目录、具有读执行行为的文件]
通过系统调用 [write] 到 [用户空间目录、具有写行为的文件]
通过系统调用 [read] 到 [系统关键目录、具有读执行行为的文件]（2跳因果链）
```

### 5.2 证据挂束，不挂边

- 模型看到“本束命中 N 个基模”，看不到“哪条成员边命中哪个 hop”。
- 最多显示 2 个基模；B1 不按覆盖率排序。
- 模型没有引用基模编号的强制要求。
- 结果是模型把证据当标签：场景 7 的文件链证据，模型却确认了整束网络流量。

### 5.3 基模角色太粗，支持度是单边的

- 角色只描述“进程有没有外联/派生/实例多少”“文件在 /tmp 还是 /usr”“网络是监听还是外连”，没有具体进程名、路径、IP、端口。
- “历史先验”只写“在 K 个训练场景出现过”，不写“命中里多少是背景边/多少是攻击边”。
- 一条规则可能在训练池里命中上万条背景边，提示词看不出来；模型会把它当强证据。

### 5.4 硬编码提示与过滤

- `has_shell_parent` 用子串匹配：`"sh" in p` 会命中 `sshd/ssh/dash/shutdown`；`cron` 也被当成“交互式会话/网络应用”。
- `请判 all` 是直接命令模型判整束相关，不是中性证据。
- token 过滤 `unit-root/dpkg/apt/systemd-timedated/fstrim/update-notifier/motd/fwupdmgr/system-generators` 把场景 4 的 apt/dpkg 攻击链整段删掉。
- 管道双端公理在场景 10 新增 1,191 条边，只有 2 条命中 GT；CA 证书边 245 条，0 条命中 GT。
- 这些是 B1 的一部分；做 LightRAG 对比时要么固定不变，要么单独消融，不能混在一起讲故事。

### 5.5 评分口径

- 报告写的是 `effects`（复数），`score_report_product.py:81` 读的是 `edge.get("effect")`（单数），所以 10 场景 18,129 条“正确边”全部是 `effect=None`，成败从未核验；实际是三元组去重，不是四元组。
- GT 里场景 7（6 条）、8（2 条）、10（2 条）的 `(path)` 格式条目没有规范化；`path_part()` 只剥容器前缀，不剥 `(path)` 后缀。所有系统都被这些条目扣分。
- 查准是“满足 GT 规则的边 / 上报去重三元组”，不是“人工核验过的真实攻击边”。
- Hybrid 来自 `output/navigator-runs/loo-hybrid/summary_hybrid.json`，是运行产物，不是官方冻结基线；项目规则明确运行产物不得当基线。
- `tmp/run_all_v4_experiment.py` 的 `hit_total` 已修；旧的 `summary_v4.json` 是 10 个场景全部 `KeyError: 'hit_total'` 的失败汇总，不要引用。

### 5.6 单次运行与随机性

- B0/B1 都是单次 LLM 运行，温度 0 但 API 仍可能有波动。
- 场景 2/7/9 的小差异（2–9 条边）可能是随机波动；场景 3（540 条）、场景 1（108 条）、场景 10（209 条）是较大的行为变化，但仍是单次。
- 不能把 +0.59 点查准当成统计显著；论文里要写“初步观察”，或者重复运行给出波动范围。

### 5.7 A 组只有 4 个场景

- A（无证据）只跑了 1/5/7/9，且 1/5/7 在 16:39–16:48 生成，早于 17:46 的代码改动。

### 7.2 四个接入点

1. **证据映射**：把 `rule_evidence_map` 从“边 → 一个基模文字”换成“边/小束 → 检索到的规则子图”。返回：motif 节点、逐跳角色、命中的具体成员边、覆盖率、支持度、精度/负例统计、ATT&CK 技术、历史案例。
2. **提示词注入**：把 `custom_render_v4` 的束级证据块换成边级/跳级块：
   - 这条边命中哪条规则的哪一跳；
   - 规则角色与这条边端点是否对得上；
   - 该规则历史命中多少攻击边/多少背景边；
   - 要求模型逐边确认并引用规则编号；
   - 没有列边的整束 `all` 不认。
3. **判断粒度**：用 `LevelKey` 的第 5 级（单边）或“小同质束”（例如 ≤20 条边），不要用上千条的大束。否则证据和束的主体对不上，模型还是当标签用。
4. **KG 存储**：
   - 节点：基模、ATT&CK 技术、案例、实体、角色。
   - 边：基模逐跳、基模→技术、基模→案例、技术→案例、实体→实例。
   - 属性：支持场景、覆盖边数、攻击/背景精度、负例数、跳数、角色链、syscalls。
   - 种子：现有折库 + 10 个场景 GT 攻击边。
   - 先给 40.5% 没被覆盖的 GT 边做 ATT&CK 映射；补不上，LightRAG 没有证据可检索。

### 7.3 评估

- **检索层**：对每条 GT 攻击边，正确基模/ATT&CK 技术是否在 top-k？当前 `gt_edge_coverage` 是符号匹配上限（59.5%），KG 应报告新的覆盖率。
- **内容层**：`B_rag − B1`，同一闭包、同一折库、同一模型、同一图公理；逐条差异，不只看微平均。
- **标签层**：`B1 − B0` 已经说明标签效应很大；`B_rag` 必须证明内容在标签之上还有增量。
