# 第一层形式化与召回上限对照

## 0. 一句话结论

从终点事件往回走这件事，其实只需要**一条规则**：

> 一条边写下的东西，后来被另一条边读走，那么前一条边就可能影响后一条边。

围绕这条规则，本文要交代四件事：

- **它够不够**：够。往回找的过程就是不停地把"写过某样东西"的边接在"读过这样东西"的边前面；接不上的地方只有两处，而这两处都不是规则不够，是图上两个本该是同一个东西的顶点没有被认成同一个（本机连接的两端、`/proc/<进程号>/` 这类对象）。补救办法是修身份，不是加规则。
- **它什么时候保证不漏**（第 3 节）：只有三句前提——攻击链的每一步都是图上的一条边；被依赖的那样东西在图上是一个顶点、而且身份已经归一；改写它的动作都被记录下来。这三句是假设，不能从图上推出来，只能声明并在数据上检验。
- **它什么时候会漏**（第 3.2 节）：列出五类。它们都是"图上根本没有那样东西"或"那次改写没有被记录"，属于采集与建模的问题。
- **它对召回意味着什么**（第 4.1 节）：判定器只能确认摆在它面前的边，所以召回的上限就是候选表覆盖标注的比例；这个上限能在跑判定之前算出来。召回损失分成"闭包侧"和"判定侧"两块，而且每一分损失都能定位到一条具体的边。

还有一层必须讲明白的取舍：当前实现会**主动丢边**，只有两处，都不是保证的一部分，是为了压小候选表而声明的精度取舍：**非交付通道不展开**（第 4.2 节第一条）与**零字节读条目剔除**（第 4.2 节第二条）。历史上还启用过七条过滤器（读动态库、系统程序自执行、系统例行文件、写非交付通道的记录直接不收、读主体伪文件连边都不收等）以及"子进程把关"，现已全部删除；它们作为取舍的性质与这两条相同。

§5 的对照实验里，两侧都是本次测量的数字：第一层按**当前工作区代码**现场重跑（不调模型）；引擎那一列是**只读已有产物重新打分**——图取自 `output/baseline/<场景>/baseline.json`，没有重跑引擎流程。两侧用同一份标注、同一个评分函数，口径与跑法写在 §5.1 表下。

## 1. 图里有什么

### 1.1 三类顶点、五条边

图上的顶点分三类。**进程顶点**代表一个进程实例，身份是"进程号加进程名"。**文件对象顶点**代表一份可以被读过又写过的内容，身份是归一化之后的路径；管道和带路径的本地套接字也归在这一类。**网络端点顶点**代表一条连接的一端，身份是"本地地址与端口，加上远端地址与端口"这四个值拼成的字符串。

边只有五种，每种的两个端点是什么、方向朝哪边，都是固定的：

| 边的类型 | 起点 | 终点 | 意思 |
|---|---|---|---|
| 进程写文件 | 进程 | 文件对象 | 进程把内容写进这份文件 |
| 文件被进程读 | 文件对象 | 进程 | 进程从这份文件取内容 |
| 进程写网络端点 | 进程 | 网络端点 | 进程把内容发到这个连接上 |
| 网络端点被进程读 | 网络端点 | 进程 | 进程从这个连接收到内容 |
| 父进程创建子进程 | 父进程 | 子进程 | 一个进程被创建出来 |

每一类顶点就是一件"可以被写、后来又可以被读"的东西。往回找之所以能连成链，靠的就是"同一件东西"这件事。

每条边还有一个**属主进程**：写文件和写网络端点的那种，属主是起点那个进程；文件和网络端点被读的那种，属主是终点那个进程；创建子进程的那种，属主是子进程。属主不需要单独记，从边的类型就能算出来，所以不会出现"边和它的属主对不上"这种不一致。

### 1.2 每条边读什么、写什么

把每条边看成一次"取走一些东西、留下一些东西"的动作：它一定在某个进程里运行，所以它要读这个进程当时的状态（内存、寄存器、打开的文件等等），也一定会改这个进程的状态（返回值、副作用）。除此之外，它还要读它的起点那一端，或者写它的终点那一端。逐类型列出来是这样：

| 边的类型 | 读走的东西 | 写下的东西 |
|---|---|---|
| 进程写文件 | 该进程的状态 | 这份文件的内容、该进程的状态 |
| 文件被进程读 | 这份文件的内容、该进程的状态 | 该进程的状态 |
| 进程写网络端点 | 该进程的状态 | 这个端点里的数据、该进程的状态 |
| 网络端点被进程读 | 这个端点里的数据、该进程的状态 | 该进程的状态 |
| 父进程创建子进程 | 父进程的状态 | 子进程（创建就是写入） |

只有一处例外要单独说：**创建子进程的那种边，它的属主是子进程，但它读的不是子进程的状态，而是父进程的状态**。因为子进程在被创建之前并不存在，谈不上"它自己的状态被读"；子进程一开始拥有的状态，是从父进程那里复制来的。

这张表是后面所有讨论的基础：一条边"写下的东西"，就是表里右边那一栏；"读走的东西"，就是中间那一栏。

### 1.3 时间口径

每条边有两个时刻：开始时刻和结束时刻，单位是纳秒，取自同一台主机的同一个时钟，开始不会晚于结束。

两个约定必须写清楚，因为规则的时间条件依赖它们：

- **交付的时间口径**：判断"写下发生在读走之前"，用的是**写的开始时刻不晚于读的结束时刻**。原因是内核允许边写边读：读者可以在写还没结束的时候就开始收数据，只要读者拿到数据时写已经动笔。要求"写完全结束才允许读"会切掉一批真实的内容链。
- **锚点截断**：固定终点事件，记它的开始时刻为**锚点**。闭包只收开始时刻不晚于锚点的边。也就是说，与终点事件在时间上重叠、并且起点落在锚点之后的那些活动，本文不把它们当作上游。这是一条明确的边界，不是优化，也不是疏漏；被它排除的那一类在第 3.2 节第 5 条里单列。

## 2. 一条规则

### 2.1 规则

**如果一条边写下的东西，后来被另一条边读走，那么前一条边就可能影响后一条边。**

"写下的东西"取第 1.2 节表里右边那一栏，"读走的东西"取中间那一栏；"后来"按第 1.3 节的交付口径判断。两条边不能是同一条。

这里有一句必须强调：规则说的是"**可能**影响"，不是"必然影响"。所以规则宁可宽一点：宽了只是多收一些边、让判定器多做判断（损失查准），不会把真正需要的那条边漏掉。本文后面所有论证都只服务于一个方向——凡是真实存在的依赖，必须被这条规则覆盖。

### 2.2 几种常见说法其实都是它的特例

常见的写法会把往回找拆成好几条规则，比如"同一进程的先后动作可以互为因果""写入某文件的内容可以被后来读该文件的进程继承""父进程创建子进程、子进程之后的动作与父进程有关""内核按进程号暴露的对象可以影响或反映该进程的状态"。这些看起来是不同的事情，但两条边能被连起来的本质完全一样：**一方写下了某样东西，另一方后来读走了这样东西**。区别只在于这样东西是图上哪一类顶点。对应关系是：

| 常见的说法 | 前一条边写下的这样东西 | 后一条边读走的这样东西 |
|---|---|---|
| 同一进程的先后动作 | 该进程的状态 | 该进程的状态 |
| 对象交付（写文件、后来被读） | 这份文件的内容 | 这份文件的内容 |
| 创建子进程、子进程之后的活动 | 子进程 | 子进程的状态 |
| 父进程的历史接上创建那一步 | 父进程的状态 | 父进程的状态 |
| 内核按进程号暴露的对象被写入 | 该进程的状态（见 2.3 节的身份归一） | 该进程的状态 |
| 内核按进程号暴露的对象被读取 | 该进程的状态 | 该进程的状态（同上） |
| 本机连接一端的写入接到另一端的读取 | 这条连接里的数据 | 这条连接里的数据（同上） |

**结论**：这些说法没有一条是独立需要的，它们全都是同一条规则在不同顶点种类上的样子。把它们合成一条，既没有丢掉什么，也没有多出什么。

### 2.3 规则之外还需要一件事：身份归一

规则要求"同一件东西"，所以先得确定哪两个顶点是同一样东西。图上有两处天然会把同一件东西记成两个不同的顶点，必须归一，否则规则接不上。这两处都不是"规则不够"，而是身份没认对。

**第一处：本机连接的两端**。图上的网络端点，是按持有它的进程所看到的四个值命名的。一条本机连接有两个进程参与，发送方那一端被记成"发送方地址端口，指向接收方地址端口"，接收方那一端被记成反过来的一套值。这两个名字左右颠倒，其实是同一条连接。发送方写进自己这一端的数据，会被接收方从自己那一端读走；如果坚持认为它们是两个不同的顶点，规则就永远接不上——写下的东西在一处，读走的东西在另一处。

这类攻击的形状是：攻击者在本机上连一个本地服务并发出指令，服务执行这条指令，最后落到终点事件。如果两端不归一，闭包能追到服务进程自己的历史，却追不到发指令的那个进程，整条上游断掉。

**第二处：`/proc/<进程号>/` 这类对象**。它们的身份里带着一个进程号，内核按这个进程维护它们，本质上不是一份普通文件，而是那个进程的状态从文件系统的一个侧面露出来。典型的有该进程的内存、环境变量块、命令行、运行状态。有两种真实依赖会被它们挡住：

- 一个进程写另一个进程的内存（代码注入、调试器改写），被写的进程随后照着新内容行动。被写的进程**不会**把"读自己的内存"记成一条系统调用，所以图上没有一条"它读走了这样东西"的边；如果那个对象仍然是独立顶点，规则接不上。
- 反过来，一个进程读另一个进程的环境变量块或运行状态，这次读取的内容来自对方的启动与运行。读取这一侧是有的，但如果那个对象是独立顶点，"对方的历史"和"这次读取"之间也接不上。

把这类对象归一到它命名的那个进程之后，这两种依赖都变成"某条边写下了该进程的状态，另一条边读走了该进程的状态"，规则自然命中。

（还有一处容易误判的是终端：服务进程把内容写进终端，外壳进程从同一个终端读走。这一条本来就符合规则，不需要归一；它过去被"外壳读管道与终端"那条过滤器整类剔掉，那条过滤器已经删除，终端现在按能承载内容的对象处理，见第 4.2 节。）

归一这件事只需要两句话：**一条连接只算一个顶点**；**路径开头是 `/proc/<进程号>/` 的对象，算作那个进程**。它是幂等的（对归一之后的结果再归一不会变），而且可以逐条检查（连接的对面顶点在不在图上、进程号能不能定位到进程顶点）。本文把这件事记作"身份归一"，它属于数据模型，不属于因果规则。

### 2.4 规则之外还需要一条时间约定

第 1.3 节已经说了两条：交付看"写的开始不晚于读的结束"，以及只收开始不晚于锚点的边。它们的作用是让"后来"这个词有确定的意思，并且把"与终点事件同时发生"的一类排除在外。加上身份归一，本文的因果内容就是：**一条规则、一次身份归一、一条时间约定**。

### 2.5 为什么这条规则能一路连回终点

假设攻击者从入口到终点走的是一条链条，链条上每一步的形式是"后一步用上了前一步的结果"。现在看链条上相邻的两步：后一步之所以用得上前一步，无非是它读走了前一步写下的某样东西——可能是前一步所在进程的状态（也就是同一个进程的后续动作），可能是前一步写进某份文件或某个连接的内容，可能是前一步创建出来的那个进程，也可能是前一步写进某个进程的状态（经第 2.3 节的归一之后）。按第 3.1 节的前提，这样东西在图上是一个顶点，而且身份已经归一，于是它一定同时出现在前一步"写下的东西"和后一步"读走的东西"里——规则命中，前一步被接上。

从终点的前一步开始这样一环一环往前推，链条上每一步都能被找到。这就是"候选表不漏"的全部理由；换句话说，**只要前提成立，召回的上限就是百分之百，判定层不需要担心本层把该找到的边漏掉**。

## 3. 保证的范围与边界

### 3.1 保证不漏需要三句前提

这三句描述的是"图与真实执行之间的关系"，不是图内部的性质，所以不能从图上推出来，只能声明，然后在具体数据上检验。

1. **步骤可观测**：攻击链的每一步都是本次导入的图里的一条边。
2. **载体有顶点**：链条上相邻两步之间被依赖的那样东西，在图上是一个顶点，并且这个顶点就是它应有的身份——一条连接只算一个顶点；`/proc/<进程号>/` 这类对象算作那个进程。
3. **改写有记录**：凡是改写这样东西的动作，都被记成了一条边，而且这条边的关系类型和两端顶点都是对的。

检验办法：第一句和第三句用导入体检和覆盖度报告检查（有没有漏采、有没有系统调用的边没有建、端点和时刻对不对）；第二句可以用人工标注做一次"逐对检查"——把标注链按时间排好，对每一对相邻的边，输出它们命中的是哪一样共同的东西（进程状态、文件内容、连接里的数据、被创建的进程、经归一后的进程状态）。全部命中，说明在这份标注上前提成立；有对不命中，就把那一对归到下面五类之一，并计入"这份数据上放弃的召回"。这个检查只用标注，不改方法，也不用来调节规则。

### 3.2 前提不成立时丢的是什么

链条断掉的地方，必然是相邻两步之间缺少"共同的那一样东西"。具体只有五类：

1. **通道在图上没有顶点**。成对的本地套接字（没有路径的那种）、抽象命名空间的套接字、匿名共享内存、消息队列、信号量，以及把描述符传给另一个进程之后再直接读写。这些东西在图上没有任何顶点，规则无法表达。管道和带路径的本地套接字已经建了顶点，不在这类。
2. **状态改变不产生边**。信号、私有接口的状态改写、进程调度时序、内核内部结构上的改动。它们既不产生"写"的边，也不产生"读"的边，所以图上看不见。
3. **改变没有被记录**。没有建模的系统调用、被导出格式串过滤掉的事件、快照长度截断掉的载荷，以及攻击者在另一台主机上的那一步（远端的那一步本来就是链条的起点，不可能是本机日志里的一条边）。
4. **身份归一定位不到**。`/proc/<进程号>/` 里的进程号在图里找不到对应的进程顶点，归一落空。
5. **时间重叠**。依赖发生在与终点事件时间重叠、并且起点落在锚点之后的时刻，比如并发线程、流水线读写。这一类被第 1.3 节的锚点截断排除在外。

第 1 到第 3 类的共同点是"图和日志本身不含这个信息"，属于采集与建模的问题，只能用覆盖度报告去量；第 4、5 类是显式的取舍，要放宽就得改第 2.3 节的归一或第 1.3 节的锚点。

## 4. 召回上限、损失归因与精度取舍

### 4.1 召回上限与损失归因

判定器有一个天然的限制：**它只能确认摆在它面前的边**。候选表就是摆到它面前的那一堆。因此对任意一份人工标注：

> 召回不超过"候选表与标注的交集大小"除以"标注大小"。

这个上限与判定器的表现无关，只取决于候选表和标注，所以只要有标注，就能在跑判定之前把它算出来；而且它是紧的——"把候选表里属于标注的边全部确认"的判定器刚好达到它。把一减去召回写成两半，就得到：

> 一减召回 = 标注里不在候选表的比例（**闭包侧损失**） + 候选表里没被确认的标注比例（**判定侧损失**）。

两块可以分别测量。闭包侧那一块还能再往下归因到一条具体的边：

- 如果放宽全部取舍之后这条标注边仍然不在闭包里，那就是**规则接不上**：把标注链按时间排好，它到终点的每一条链都断在某一对相邻边上，输出那一对边就能看到断在哪、属于第 3.2 节的哪一类。
- 如果放宽取舍之后它本来在闭包里，那就是被**某一处取舍剪断**：沿着它到终点的一条链，一定能找到那处取舍挡住的那一条边。当前只有两处能造成这种损失，而且两处各自计数，所以每一分损失都能定位到一条具体的边：非交付通道不展开，按路径类别计数（`nondelivery_not_expanded`）；零字节读条目剔除，计数是 `stats.expand.fold.empty_read_triples_dropped`。

这也解释了为什么这两处取舍必须**分开计数**：如果几种类别共用一个计数，第二种损失就定位不出来。

### 4.2 精度取舍清单（会主动丢边的两处）

当前实现只有两处会主动丢边。它们的共同特点是：丢掉的类别在结构上与例行活动同形，无法区分，所以只能作为"按数据集启用、启用前重新核对"的可选项，不能算进保证。

| 取舍 | 丢掉什么 | 要证明它无损，需要什么条件 | 本图能不能证明 | 现状与实测 |
|---|---|---|---|---|
| 非交付通道不展开 | 从这些对象读内容的边照收进闭包，但不往回找写入者 | 这个对象不可能把写入的内容交给后面的读者 | **只能证明一半**。内核现生成的伪文件（`/proc`、`/sys`）：内容由内核在读取那一刻生成，不存在"谁写在那里等着被读"，这一半有结构依据。设备节点、系统运行目录及其中的系统级套接字：这些路径确实能在进程之间传内容（块设备、`/run` 下的套接字），判它非交付的依据是"这类活动在攻击链上几乎总是例行操作"这种分布判断，不是结构事实 | 判据表 `pagent/rules/l1_judgments.json` 已按这两半分别标注（每条判据的 `basis` 字段：`structure` / `distribution`）。放开"分档类"三档的代价与收益没有在当前数据集上测过，所以这一处只能逐数据集核对后再启用 |
| 读无关进程的运行状态数值与属性文件 | 折叠之后，把「读 `/proc/<进程号>/` 下 stat / status / current / comm / limits / attr/current 六种文件、而该进程号不在候选表里」的条目去掉 | 那些进程号确实与终点事件没有因果往来 | **不能证明**。判据有两半：一半是数据事实（这五种文件是内核现生成的运行状态数值，不是谁交付的内容），另一半是启发式（那个进程不在链上就与本次追踪无关）；后一半可以举出反例 | 当前五场景实测剔掉 740 / 370 / 1,561 / 69 / 517 条（场景 1 → 5），标注覆盖 399/434；形态是 `ps` / `ss` / `systemd` 一次扫描读几百个进程号（`stat` / `status` / `comm` / `attr/current`）、`sudo` / `su` / `sshd` 读 `/proc/1/limits`。**不删**能拿到命令行、控制组、环境变量、内存与内存布局的那些（`cmdline` / `cgroup` / `environ` / `mem` / `maps` / `fd`） |
| 零字节读条目剔除 | 折叠之后，把「全部实例都是零字节读」的内容三元组从候选表里去掉（终点事件的实例豁免） | 人工标注不会把"读到结尾"这类动作计为链路步骤 | **不能证明**。判据说的是数据事实（零字节读没有搬走任何内容，见本节末段），但"标注会怎么记"不是数据事实 | 当前五场景实测剔掉 252 / 15 / 242 / 107 / 43 条（场景 1 → 5），标注覆盖 399/434。典型例子：`ps` 读已消失进程的 `/proc/<号>/cmdline`、命令管道读到结尾、空文件被读 |

历史上曾启用的七条过滤器（读系统库目录下的动态库、系统目录下的程序执行自身、读本地化与名字解析等服务配置、服务进程读系统或运行时文件、外壳读管道与终端、对用户路径的符号链接与删除、读主体伪文件连边都不收）以及"子进程把关"，都不在规格内、也无法证明无损，所以已经从实现里删掉。它们的取舍性质与上表两条相同，删除的后果是候选表变大、召回上限不变。

有一点可以证明无损，所以保留并延伸到候选表：**读取返回零字节时，不再从这个对象往回找写入者，这类条目也不进候选表**。读取返回零字节意味着这次调用没有从对象取到任何内容，因此不存在"内容经这个对象交付"的依赖；可能存在的只是状态依赖，而状态依赖由同一条规则里"进程状态"那一项照常覆盖。

### 4.3 实现口径与上面这套规格的差别

上面讨论的是规格。实现的每一处差异列在下面。"更宽"指实现比规格收得更多，"更窄"指实现丢边。更宽的差异只会让闭包变大，不影响召回；更窄的差异是候选损失，必须进第 4.2 节的清单。

| 项 | 规格 | 当前实现 | 方向 | 对召回的影响 |
|---|---|---|---|---|
| 唯一规则 | 写下的东西后来被读走 | 按关系分三支取边（同进程、对象、派生）+ 连接建立类不算交付 | 等价，三支与排除项都是这条规则的实例 | 无 |
| 身份归一：连接的两端 | 一条连接只算一个顶点 | 未做，两个朝向各建一个顶点 | 更窄 | 有损：本机连接的跨进程链路（第 2.3 节第一处） |
| 身份归一：`/proc/<进程号>/` 对象 | 算作那个进程 | 未做，而且这类对象被整类剔掉 | 更窄 | 有损：内存注入与进程状态窃取（第 2.3 节第二处） |
| 进程的门限 | 开始不晚于锚点 | 进程一旦被触达，就取回它在锚点之前的全部事件 | 更宽 | 无 |
| 对象的门限 | 写的开始不晚于读的结束 | 同规格，另外把零字节写入也取回 | 更宽 | 无 |
| 连接建立类操作 | 是普通的内容边 | 从内容展开里排除（连接、绑定） | 更窄 | 无。这两类不携带内容；它们"把两端接起来"的作用由身份归一承担 |
| 两处取舍 | 不在规格内 | 非交付通道不展开、零字节读条目剔除（第 4.2 节） | 更窄 | 有损；两处各自计数，可定位到具体边 |

**要让实现达到第 3.1 节前提下的包含性，只需要做两件事**：把身份归一的两条补上（一条连接只算一个顶点；`/proc/<进程号>/` 这类对象算作那个进程）；把非交付通道那一处取舍按第 4.2 节改写，只保留有结构依据的那一半。两处"更宽"的差异不必改。

最后要说明一句：§5 的实测数字量的是**当前实现**（没有身份归一；规则类过滤器与子进程把关已删除，只剩第 4.2 节那两处取舍），不是上面这套规格。§5 里第一层覆盖 399/434（漏 35 步，集中在场景 1、4、2），这是对第 3.1 节前提的一次经验校验；漏掉的那些地方要按第 4.1 节的归因办法逐条定位，本次未做，所以这里不构成对规格的证明。

### 5.3 观察

1. **召回：第一层 399/434（91.94%），引擎最终图 178/434（41.01%）**；逐场景第一层都不低于引擎，差距最大的是场景 2（96.15% 对 3.85%）与场景 5（100% 对 15.83%）。
2. **第一层漏的 35 步集中在三处**：场景 1 漏 22 步（21 条必须条目 + 规则 R1）、场景 4 漏 11 步、场景 2 漏 2 步；场景 3、5 一步不漏。漏掉的地方要按第 4.1 节的归因办法逐条定位到"规则接不上"或"被某一处取舍剪断"，本次未做归因。
3. **查准必须连着阶段读**：第一层是判定前的候选池（五场 36,364 条去重三元组），引擎最终图是取交与时间窗合并之后的交付图（4,421 条）。只算命中必须条目边时，第一层 1.09%、引擎 3.98%——引擎的图小得多，这是它查准更高的主要原因，不是同一阶段上的优劣。
4. **规则会显著抬高口径查准**：场景 1 第一层 92.29% 里，12,128/13,203 来自规则 R2 一条；引擎最终图里一条 R2 边都没有，所以它的 11.70% 全部来自必须条目。
5. **引擎最终图更"小而准"的场景是 1、3、4**：三元组 376 / 206 / 894，命中条目 44 / 76 / 33，代价是召回 55.00% / 77.78% / 51.56%；场景 2、5 则是量与命中都低（召回 3.85% / 15.83%）。
6. **第 4.2 节两处取舍在五场景上的实测计数**：读无关进程的运行状态数值与属性文件剔除 740 / 370 / 1,561 / 69 / 517 条（场景 1 → 5），零字节读条目剔除 252 / 15 / 242 / 107 / 43 条；这批运行里第一层覆盖 399/434，也就是两处取舍都在生效的前提下量的。
7. **可复现**：第一层 `tmp/provenance-agent/l1-vs-engine/measure_l1.py --scenario <场景全名>`（不调模型），规则边拆分与引擎侧打分 `tmp/provenance-agent/l1-vs-engine/breakdown.py`；引擎侧要用同一份代码重跑后向、前向与交集，流程见 `progql-local/baseline/README.md`。
