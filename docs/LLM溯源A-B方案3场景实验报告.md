# LLM 溯源 A/B 方案 3 场景实验报告

- 实验日期：2026-11-04
- 模型：`deepseek-v4.1-flash`，温度 0
- 基线：`output/navigator-baseline/summary_rules.json`（正式 `rules` 基线）
- 实验目录：`tmp/llm_trace_ab/`
- 评分工具：`tools/score_report_product.py`
- 场景数：3 个（从 10 个场景中选取）
- 运行次数：每个变体每个场景 1 次

---

## 结论摘要

本轮实验没有证明“纯 LLM 方案整体优于 rules 基线”。

具体结论：

1. **A 方案（程序扩展图 + LLM 逐批判定）不如 rules。**
   3 场景微平均召回 28.8%、查准 27.4%，rules 为 77.4%、69.7%。

2. **B 方案（LLM 规划查询 + 程序执行）不是全面不如 rules。**
   3 场景微平均查准 76.4%，高于 rules 的 69.7%；但召回 31.8%，远低于 rules 的 77.4%。
   B 是“查准优先”的方案，不是“召回不降”的替代方案。

3. **B 比 A 好。**
   3 场景微平均 B 为 31.8% 召回 / 76.4% 查准，A 为 28.8% / 27.4%；B 在召回和查准上都高于 A。

4. **只有场景 7 出现 LLM 方案在两个指标上都超过 rules。**
   `7_DB_Bruteforce_Datawipe`：B 为 24.7% 召回 / 52.9% 查准，rules 为 19.2% / 33.3%。

5. **场景 1 是明确负结果。**
   `1_Web_Exploit_Ransomware`：B 为 13.9% 召回 / 51.9% 查准，rules 为 90.1% / 76.3%。
   B 没有新增命中，丢失了 75 个 rules 已命中步骤。

6. **主要限制来自实现和预算，不是单一“模型能力”结论。**
   A 没有 CTI/MITRE/Kill Chain 知识库，B 没有 CTI 报告检索；B 的查询预算只有 8 步；每个变体只跑 1 次。
   因此本轮结论是“当前实现、当前预算、这 3 个场景下的结果”，不能直接外推为论文方法本身的上限。

## 1. 实验目的

本轮要回答四个问题：

1. A 方案相对 rules 基线，召回和查准如何变化？
2. B 方案相对 rules 基线，召回和查准如何变化？
3. 在同一模型、同一预算口径下，A 和 B 哪个更好？
4. 变化到底来自 LLM，还是来自候选池、模板查询等非 LLM 部分？

为了回答问题 4，除了 A 和 B，还跑了两个不调用 LLM 的控制组：

- **A0**：与 A 相同的图扩展规则和预算，但保留全部候选边。
- **B0**：用固定模板查询做广度扩展，查到什么就上报什么，不做 LLM 规划，也不做 LLM 最终裁决。

---

## 2. 场景选择

从 10 个场景中选了 3 个，覆盖三种基线形态：

| 场景 | rules 召回 / 查准 | 选择理由 |
|---|---:|---|
| `1_Web_Exploit_Ransomware` | 90.1% / 76.3% | 高召回、高查准、大图，测“能否保住精度” |
| `5_Exposed_Service_Pivot` | 95.7% / 9.0% | 高召回、极低查准，测“能否大幅提精度而不丢太多召回” |
| `7_DB_Bruteforce_Datawipe` | 19.2% / 33.3% | 低召回、小图，测“能否补召回” |

选择依据是 rules 基线在这 3 个场景上的表现分布，不是 A/B 的运行结果。

## 3. 两个方案的做法

### 3.1 A 方案：程序扩展图，LLM 逐批判定

A 对应 TRACKAGENT 的核心机制。

执行流程：

1. 从 POI 开始。POI 是入侵检测告警对应的那个事件，来自 `provenance-navigator/config/scenarios.json`。
2. 程序沿因果边做一跳扩展。扩展顺序由程序决定，不由大模型决定。
3. 每次取当前节点附近的一批事件，最多 20 条，交给大模型。
4. 交给大模型的内容包括：
   - POI 描述；
   - 当前调查摘要；
   - 已经出现的攻击阶段列表；
   - 这批事件的源、系统调用、目标、端点类型、成败、相对 POI 的时间；
   - 如果端点是进程，还包括可执行路径、命令行、父进程号。
5. 大模型逐条回答“保留还是丢弃”，并给出置信度、攻击阶段、简短理由，同时更新调查摘要。
6. 程序只沿着“被保留事件”的另一端继续扩展。被丢弃的事件不再往后查。
7. 停止条件三选一：
   - 没有新的节点可扩展；
   - 调用次数达到 60 次；
   - 已判定事件达到 1,200 条。
8. 把保留的事件作为最终结果上报，用官方评分器算召回和查准。

控制组 A0：

- 使用相同的扩展规则、节点排序、每节点上限和 1,200 条总上限；
- 每个批次直接全部保留；
- 因为 A0 保留全部边，它的队列会比 A 更宽，后续访问到的节点也会不同；
- 不调用大模型。

因此：

- A0 反映“这套图扩展本身能覆盖多少”；
- A 反映“LLM 逐批判定后，精度提高多少、召回损失多少”。

### 3.2 B 方案：LLM 规划查询，程序执行查询

B 对应 Minos 的核心机制。

执行流程：

1. 先从 POI 自动取一次它的一跳邻域，作为初始证据。这一步是程序做的，不调用大模型。
2. 大模型 Planner 查看当前证据、调查摘要、攻击阶段、还没查过的节点，提出下一步调查方向。
3. 第二个大模型把调查方向翻译成一条只读图查询。
4. 程序执行查询，但先做限制：
   - 只允许读，不允许写；
   - 先统计候选数量，超过 5,000 就拒绝；
   - 每次最多返回 200 行；
   - 重复查询直接拒绝；
   - 查询报错就把错误回给大模型，让它修正一次。
5. 查询结果去重后加入证据集。
6. 大模型更新调查摘要和攻击阶段。
7. 最多走 8 步，或证据达到 1,200 条。
8. 从证据里挑出最接近 POI、风险较高、时间较近的最多 200 条，交给三个大模型角色：
   - 一方只找“这些边是恶意的”理由；
   - 一方只找“这些边是良性的”理由；
   - 第三方看双方理由，决定最终上报哪些边。
9. 最终上报边用官方评分器算召回和查准。

控制组 B0：

- 用固定模板查询做广度扩展；
- 不调用 Planner，不生成自由查询，不做最终裁决；
- 查到的事件全部上报；
- 最多 10 个扩展节点、1,200 条证据。

因此：

- B0 反映“固定模板查询能覆盖多少”；
- B 反映“LLM 规划查询 + 最终裁决”带来多少变化。

### 3.3 两个方案的关键差异

| 维度 | A | B |
|---|---|---|
| 谁决定下一步扩展 | 程序按一跳邻居扩展 | 大模型 Planner 决定查什么 |
| 大模型输入 | 20 条事件 + 调查摘要 + 攻击阶段 | POI + 已有证据 + 未查节点 + 历史指令 |
| 大模型输出 | 每条事件保留/丢弃 | 调查方向 → 查询语句 |
| 程序职责 | 扩展、记录、评分 | 只读校验、数量预检、行数限制、去重、错误回传 |
| 长历史状态 | 调查摘要 + 攻击阶段列表 | 调查摘要 + 攻击阶段列表 |
| 最终筛选 | 逐批 LLM 判定 | 控方 / 辩方 / 裁决 |
| 控制组 | A0：同遍历全保留 | B0：模板查询全上报 |

## 4. 实验设置

### 4.1 预算

| 项 | A | B |
|---|---|---|
| 模型 | `deepseek-v4.1-flash` | 同左 |
| 温度 | 0 | 0 |
| 总预算 | 60 次调用、每批 20 条、最多 1,200 条判定 | 8 步、每步最多 200 行、最多 1,200 条证据 |
| 单节点上限 | 每个节点最多 40 条边 | 不适用 |
| 最大闭包距离 | 8 | 不适用 |
| 最终筛选 | LLM 逐批 keep/drop | 控方/辩方/裁决，最多 200 条候选、50 条一批 |

A 和 B 的事件预算都在 1,200 条左右，但预算形式不同：A 是“判定事件数”，B 是“收集证据数”。

### 4.2 防泄漏

提示词和运行过程中不包含：

- 真实场景名；使用不透明 `case_<hash>` 标识；
- 进程原始标识串；它包含场景主机名，全部换成 `P1`、`P2` 等局部别名；
- `groundtruth/` 的任何内容；
- `output/navigator-baseline/` 的任何内容；
- 基线的判定字段，例如 `origin`、`class`、`reason`、`channels`、`dist`、`via`。

标准答案只在大模型运行结束后的评分阶段读取。

### 4.3 评分口径

- 召回（按步骤）：命中的标注步骤数 / 标注步骤总数。
- 查准（按四元组）：命中的 `(源, 系统调用, 目标, 成败)` 数 / 上报去重四元组数。
- 跨场景汇总使用微平均：先把所有场景的分子、分母分别相加，再相除；不平均每个场景的比率。
- 不合成 F1。
- 逐场景差分按标注内容三元组计算：
  - `gained`：rules 没命中、变体命中的步骤；
  - `lost`：rules 命中、变体没命中的步骤；
  - `extras`：变体上报但 GT 不认的边数。

在跑 A/B 之前，先量了每个场景的完整反向因果闭包规模，以及“把闭包全部保留”能到的召回上限。

| 场景 | 闭包边数 | 闭包召回上限 | 闭包查准参考 | rules 召回 / 查准 |

- 场景 7 的闭包召回上限 90.4%，rules 只有 19.2%，补召回空间最大。
- 场景 5 的闭包召回上限 99.4%，rules 95.7%，主要空间在查准。

## 7. 逐场景结果

| 场景 | rules | A | A0 | B | B0 |
|---|---|---|---|---|---|
| `1_Web_Exploit_Ransomware` | **90.1% / 76.3%** | 52.5% / 30.5% | 56.4% / 8.9% | 13.9% / 51.9% | 5.0% / 1.3% |
| `5_Exposed_Service_Pivot` | **95.7% / 9.0%** | 20.9% / 18.7% | 26.4% / 3.5% | 46.0% / **94.9%** | 50.3% / 23.5% |

逐场景说明：

1. **场景 1**
   - rules 在召回和查准上都最好。

   - B 的召回只有 13.9%，查准 51.9%；没有新增命中，丢失 75 个 rules 已命中步骤。

3. **场景 7**
   - rules 召回 19.2%、查准 33.3%。
   - B 召回 24.7%、查准 52.9%，召回和查准都超过 rules。
   - A 查准 90.9%，但召回只有 13.7%，低于 rules。
   - 这是唯一一个 LLM 方案在两个指标上都超过 rules 的场景。

定义：

## 10. 结果解释

### 10.1 A 为什么不如 rules

A 的问题分成两层：

1. **图扩展本身覆盖不足。**
   A0 用同一套扩展、保留全部边，召回只有 40.4%。这说明 A 的遍历顺序、每节点 40 条上限、最大距离 8 跳，已经把候选范围限制在 rules 之下。
2. **LLM 过滤进一步压低召回。**
   A0 到 A，查准从 8.4% 提到 27.4%，但召回从 40.4% 掉到 28.8%。
   场景 5 丢失 128 个 rules 已命中步骤，场景 1 丢失 44 个。
   原因是 A 只在“保留事件”的另一端继续扩展；早期丢弃一条真实攻击边，后面的整条链都不会再被判定。
   场景 7 只用了 13/60 次调用，就是队列提前耗尽的直接结果。

所以 A 的精度提升是真实的，但它用召回换精度，换得太多。

### 10.2 B 为什么查准高、召回低

B 的最终裁决机制效果明显：

- B0 到 B，查准从 12.7% 提到 76.4%，召回几乎不变（31.2% → 31.8%）。
- 场景 5：查准从 23.5% 提到 94.9%，召回从 50.3% 降到 46.0%。
- 场景 7：查准从 18.4% 提到 52.9%，召回保持 24.7%。

但 B 的召回受查询覆盖限制：

- 场景 1 只有 104 条证据、27 条保留，8 步查询覆盖不了这条大攻击链；它没有新增命中，丢失 75 个 rules 步骤。
- 场景 5 只有 348 条证据、79 条保留；它找到了 75 个标注步骤，但 rules 找到了 156 个。
- 场景 7 的证据只有 59 条，但足以找到 18 个标注步骤，并保持较高查准。

因此 B 的瓶颈是“查到多少”，不是“判得准不准”。裁决机制已经证明有效，缺的是查询预算和知识引导。

### 10.3 A 和 B 哪个更好

按 3 场景微平均：

- B 召回 31.8%，A 28.8%；
- B 查准 76.4%，A 27.4%。

B 在召回和查准上都高于 A。逐场景：

- 场景 1：A 召回 52.5% 高于 B 的 13.9%，但查准 30.5% 低于 B 的 51.9%；
- 场景 5：B 召回 46.0%、查准 94.9%，明显优于 A 的 20.9%/18.7%；
- 场景 7：A 查准 90.9% 高于 B 的 52.9%，但召回 13.7% 低于 B 的 24.7%。

综合看，B 是两者中更好的方案。

### 10.4 相对 rules 的定位

- **rules 是召回优先的基线**：77.4% 召回、69.7% 查准，0 次模型调用。
- **B 是查准优先的方案**：76.4% 查准、31.8% 召回，约 16 万 token。
- **A 是低召回、低查准的方案**：28.8%/27.4%，不建议作为替代。

如果要求“召回不能明显低于 rules”，A 和 B 都不合格。
如果允许“先高精度上报，再人工补召回”，B 在场景 5 和 7 有实际价值。
如果要求“两个指标同时不低”，只有 B 在场景 7 做到了。

## 11. 与论文的对应和偏差

### 11.1 A 对应 TRACKAGENT

已实现：

- 程序做一跳扩展；
- LLM 每批最多 20 条事件；
- 近期调查摘要；
- 攻击阶段列表；
- 每条事件保留/丢弃；
- 严格结构化输出；
- 保留事件继续扩展。

未实现：

- CTI 报告、MITRE TTP、日志模式三类文档的向量检索；
- TRACKAGENT 的原始提示词；
- Kill Chain 知识库；
- token 成本的细粒度分析；
- 3 次重复运行。

因此 A 是“TRACKAGENT 核心机制”的复现，不是完整复现。没有知识检索，会直接削弱它在语义模糊场景下的判断能力。

### 11.2 B 对应 Minos

已实现：

- Planner / Query 分离；
- 先规划调查方向，再生成查询；
- 查询数量预检、行数限制、只读校验；
- 查询报错回传并修正；
- 近期摘要 + 攻击阶段列表；
- 控方 / 辩方 / 裁决三角色最终筛选；
- MITRE 技术编号引用检查。

未实现：

- CTI 报告向量库；
- 对每条事件都做三方辩论；本轮只在最终候选集上做；
- 完整有限状态机终止条件；
- Minos 的 75 轮上限；本轮只有 8 步；
- 3 次重复运行。

因此 B 是“Minos 核心机制”的复现，不是完整复现。查询预算和 CTI 知识缺失，是它召回低的主要原因。

## 12. 限制

1. **只测了 3/10 个场景。**
   本轮结果不能代表完整基准，也不能直接外推到其他攻击类型。

2. **每个变体每个场景只跑 1 次。**
   温度为 0，但大模型输出仍可能波动；本轮没有 3 次重复，也没有置信区间。

3. **A 的候选范围是受限的。**
   A 只处理闭包的一个子集，每节点最多 40 条边、最大 8 跳、总判定 1,200 条；场景 7 因队列提前耗尽只用了 13 次调用。

4. **B 的查询预算只有 8 步。**
   Minos 论文的轮数上限远高于 8；场景 1 的低召回很可能是预算问题，而不是规划机制本身失效。

5. **A/B 的候选池不同。**
   A 使用缓存的反向闭包；B 直接查询图数据库；rules 使用自己的符号规则库。三者不是同一个候选池上的受控消融。

6. **知识组件缺失。**
   A 没有 CTI/MITRE/Kill Chain 知识库，B 没有 CTI 报告检索；这会让本轮结果低于论文方法的完整能力。

7. **静态 MITRE 列表很小。**
   B 的引用检查只针对一个固定的小列表，不能覆盖完整 MITRE ATT&CK。

8. **A0/B0 是控制组，不是正式基线。**
   A0/B0 只用于判断 LLM 的增量贡献，不作为对外成绩。

---

## 13. 结论

1. 在本轮 3 个场景、单次运行、当前实现和预算下：
   - **A 不如 rules**；
   - **B 的查准高于 rules，但召回明显低于 rules**；
   - **B 好于 A**；
   - **只有场景 7 的 B 在两个指标上都超过 rules**。

2. 不能据此得出“论文方法本身不如 rules”的结论。A 缺少知识检索，B 缺少 CTI 知识库和足够查询预算；两者都只跑了 3 个场景、1 次。

3. 如果目标是替代 rules：
   - 纯 A 不可行；
   - 纯 B 只能作为“高精度、低召回”的方案，不能直接替代 rules。

4. 如果目标是提升现有系统：
   - 更现实的方向是 **rules 保召回 + B 做高精度复核/补充**；
   - 或者给 B 增加查询步数、补 CTI/MITRE 知识库，再测 10 场景 3 次。
