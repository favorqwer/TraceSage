用途：决定哪些数据集应删除、哪些需要保留/改造，为后续"真实且复杂"的新数据集让路。

## 1. 评审口径（七条尺子）

1. **初始访问真实性**：攻击者是否真的在"网络另一端"（存在攻击者→受害者的入向连接），还是受害者在本地自己下载并运行脚本。
2. **Kill-chain 覆盖度**（满分 12）：侦察、初始访问、落地执行、持久化、提权、凭据访问、发现、横向移动、收集、外传、影响、反取证。
3. **时长来源**：耗时是否来自真实工作（扫描/爆破/传输/加密），还是 `sleep`/`timeout` 空转。
4. **数据流向**：窃取的数据是否真的流向攻击者（网络出边），还是只写受害者本地文件。
5. **攻击信号浓度**：攻击相关进程事件占全日志的比例（决定图里信噪比，也决定评测难度是否真实）。
6. **GT 可用性**：是否有 `*.groundtruth.json`（没有就无法被 `tools/evaluate_gt.py` 评分）。
7. **时长是否匹配目标**：目标 60–150 min，用于长时窗/时序因果评测。

## 3. 逐场景诊断

### 场景 1 — Multi-Stage Data Exfiltration（3.01 GB / 2.8 min）

- 攻击内容：`wget` 拉载荷 → `mv` 改名隐藏 → `chmod` → 执行 → `cp /etc/passwd` → `tar|gzip` → `cat|nc` 外传。
- 硬伤：① 命令是**在 Ubuntu 本地终端逐条敲的**（文档原文："或者直接在 Ubuntu 的另一个终端中执行"）——
  攻击者根本不参与网络，图里只有"受害者自己下载 + 自己外传"；② 无侦察、无凭据、**无提权**
  （读的是全局可读的 `/etc/passwd`）；③ 无持久化；④ 采集窗仅 **2.8 分钟**，无 dwell；
  ⑤ 载荷是为测试手写的 5 行脚本，不是真实工具。
- 唯一价值：它是**整个项目的回归参照系**——官方 `baseline.json`、POI、GT（32 条）、
  `evaluate_gt.py` 默认 GT、AGENTS.md 第 7 节全部口径都挂在它身上。
- **判定：保留。删它等于重做验证体系。**

### 场景 2 — Masquerade Data Exfiltration（4.59 GB / 2.6 min）

- 攻击内容：与场景 1 几乎同构（wget → 脚本 → 读 `/etc/passwd` → 外传），只多两件事：
  自我复制到 `/tmp/.sys_kernel_check_v2`、`base64` 编码后用 `curl -X POST` 回传。
- 硬伤：① 载荷内显式写了 `sleep 60` 并标注"【时间规避】"——教科书式的凑时长；
  ② 外传内容是 base64 后的 5 行 `/etc/passwd`（几十字节级），无真实数据体量；
  ③ 无提权、无持久化（自我复制后立刻 `rm`）；④ 与场景 1 的进程链几乎完全重合，**信息增量最低**。
- 唯一价值：GT（32 条）+ `connect EINPROGRESS` 修复的复验样本。
- **判定：删除日志本体。结论、GT、对比报告已在文档中固化；若将来还要改解析器重测，再从
  Neo4j 图 dump 出发即可（见 §5）。**

### 场景 3 — SSH Spray（6.80 GB / 40 min）

- 攻击内容：`hydra` 低速喷洒 → 弱口令成功登录 → **远程命令执行**（`sshd → bash -c`）→
  mkdir + 系统/身份枚举 + `find /etc` → 结果落盘本地。
- 优点：**六个场景里唯一"攻击者真的在网络另一端"的**（7,000+ 行入向连接事件）；
  40 分钟真实时长；有 48 条 GT（2026-09-11 新做，逐事件核对过）。
- 硬伤：① 喷洒阶段是 `while true; hydra; sleep 60` 循环，一半时间是空转；
  ② 登录后只有 `date/whoami/id/uname/find/stat`，**没有提权、没有持久化、没有敏感数据收集、
  没有外传**（输出被刻意限制在本地"实验目录"）——攻击没有目标，只有侦察；
  ③ 弱口令 `labssh` 是预置的，无发现过程（无侦察、无口令复用来源）。
- **判定：保留，并且它是"改造成完整链路"性价比最高的一个：已有真实入口 + 已有 GT，
  只需往后接"提权 → 持久化 → 收集 → 外传 → 影响"，就能变成一条真实的完整攻击链。**

### 场景 4 — Site Defacement（7.20 GB / 23 min）

- 攻击内容：用 `labweb` 凭据 `sshpass ssh/scp` 上传发布包 → 远端 `tar/cp` 覆盖站点 → 写 marker。
- 硬伤：① 场景前提就是"**已获实验账号**"，入口直接跳过；
  ② 无提权（全程 labweb 权限）、无持久化、无横向、无数据窃取；
  ③ 链路极短：本质是"scp 一个 tar 包并解包"；
  ④ **日志里 51% 的事件来自 `unattended-upgr`**（Ubuntu 自动更新），最大贡献者与攻击无关；
  ⑤ 无 GT，无法评分。
- **判定：可删。** 站点篡改这一影响面已被新场景 7 的 P11 覆盖（且场景 7 是提权后以 root 篡改）。

### 场景 5 — User Timer Resource Hijack（5.81 GB / 28 min）

- 攻击内容：下载"诊断更新包" → 装用户态 systemd service+timer（4 分钟周期）→ 每次触发跑 `worker.sh`。
- 硬伤：① **载荷行为是纯粹的人工 busywork**：`dd if=/dev/zero` 写 96 MB 零块、
  `dd if=/dev/urandom` 写 24 MB、对同一文件重复 `sha256sum` 四次、`gzip` 一个文本文件、
  `tar` 打包——这些不是任何真实攻击者会做的事，是为了"造边"而造的流量；
  ② 初始访问仍是本地"管理员执行 install.sh"；③ 无 C2、无外传、无凭据、无提权；
  ④ 无 GT。
- 唯一价值：用户态 timer 持久化 + 多轮周期触发。
- **判定：删。** 该能力已被场景 7 覆盖（systemd system timer + 用户 crontab + 每次触发跑真实载荷：
  限速外传/加密/破解），而且场景 7 的每轮触发都有真实目的。

### 场景 6 — SQLite Pipeline Pollution（2.27 GB / 9 min）

- 攻击内容：`curl` 拉 bundle → `sqlite3` 导入 8 万行 CSV → 4 条 SQL 报表 →
  `awk/sed/sort` 管道 → 汇总 → `tar` 归档。
- 硬伤：① **这不是攻击，是一段正常的数据处理流水线**：没有远程访问、没有凭据、没有提权、
  没有持久化、没有异常行为，全部落在家目录；② 名字叫 "Pollution" 但没有任何**完整性污染**动作
  （没有注入脏数据、没有篡改库内容）；③ 用 `awk/sed/sort/gzip` 的批量文件读写充数，9 分钟产出 7.1 M 事件；
  ④ 无 GT。
- 唯一价值：如果想研究"良性重负载下的假阳性"，它可以当中等质量的噪声基线（但其中 46% 是桌面噪声，质量不高）。
- **判定：删（若要假阳基线，应专门采一份干净的良性负载，而不是沿用这份）。**

## 4. 三个结构性问题（比单个场景的问题更严重）

1. **六分之四是"本机自演"**：场景 1/2/5/6 的攻击命令都在受害者本地执行，攻击者从不在网络上出现。
   图里的网络实体只有"受害者主动下载载荷"和（1/2 的）一次性回传。**没有入向连接 = 没有真正的初始访问**，
   这类数据无法评测"外部入侵检测"，只适合评测"内部可疑行为"。
2. **时长与"长时攻击"目标完全不匹配**：2.8 / 2.6 / 9.1 / 23.2 / 28.4 / 40.1 分钟，
   没有一条达到 60 min，最长的一条还只有侦察阶段。且场景 3/4/5 的时长主要来自
   `sleep 60` 循环 / `timeout` 空转 / 定时器周期，而不是真实工作量。
3. **攻击信号被环境噪声淹没**：每个场景都有 **22–47%** 的桌面/GUI 事件
   （gnome-shell、Xorg、firefox、tracker-miner、gjs…），场景 4 更有 51% 来自 `unattended-upgr`。
   攻击进程占比仅 **0.3% / ≈0% / 18.7% / 2.1% / 5.2% / 3.2%**。
   后果：图规模被无关顶点撑大（场景 4 有 3,887 个 Process 顶点、412,670 条边，而攻击只占 2%），
   召回/查准的分母失真，且评测成本被噪声占据。

## 5. 删除清单与前置动作

### 建议删除

| 对象 | 大小 | 说明 |
|---|---|---|
| `input/sysdig/2_Masquerade_Data_Exfiltration.jsonl` | 4.59 GB | 与场景 1 同构，仅多 base64+POST+`sleep 60` |
| `input/sysdig/5_User_Timer_Resource_Hijack.jsonl` | 5.81 GB | 人工 busywork，能力已被场景 7 覆盖 |
| `input/sysdig/6_SQLite_Pipeline_Pollution.jsonl` | 2.27 GB | 正常 ETL 流水线，不是攻击 |
| `input/sysdig/4_Site_Defacement.jsonl`（可选） | 7.20 GB | 短链路 + 51% 与攻击无关的自动更新噪声 |

合计回收 **12.7 GB（必删）/ 19.9 GB（含 4）**。

### 必须保留

- **场景 1**：回归基线（`baseline.json`、AGENTS.md 第 7 节全部口径、默认 GT）。
- **场景 3**：唯一真实远程入口 + 40 min + 48 条 GT，改造为完整链路的载体。

### 删之前必须先做（否则断证据链）

1. **先把"图"固化，再删日志**：日志比图大 2–3 个数量级。对要删的场景执行
   `python tools/dump_neo4j_content.py --database tracesage-<场景名>` 导出规范化 JSON，
   或对 Neo4j 库做 `neo4j-admin database dump`。这样保留的是可比对的内容，
   扔掉的只是可再生的原始日志。
2. **确认论文/报告没有引用被删场景的原始日志**（`paper/` 与 `output/` 中的引用先自查）。
3. **保留 GT 与场景文档**：`groundtruth/2.*`、`3.*` 等文档与 GT 文件与被删日志并不绑定，
   删日志不影响它们作为方法记录的价值。

## 6. 对"真实且复杂"的建议路线

1. **以场景 3 为骨架做补全**（成本最低）：保留其真实远程入口与喷洒节奏，
   把"sleep 60 循环"换成大字典真实爆破（见场景 7 的 `hydra -t 4 -W 3` + 1200 口令），
   登录后接：提权 → 持久化 → 凭据收集 → 横向 → 限速外传 → 影响 → 反取证。
2. **新数据集按场景 7 的模板造**：真实外部侦察 → 应用层利用 → 落文件 → 反向 shell →
   双路径提权 → 多持久化 → 多渠道限速外传 → 勒索/篡改，时长由数据体量、字典规模、
   传输限速、逐文件加密次数决定（见 `groundtruth/7.SQLi WebShell Ransomware.md` §1）。
3. **采集环境加固**（这是提升"攻击信号浓度"最有效的一步，比换攻击手法更立竿见影）：
   - 受害者用 **Ubuntu Server 最小安装**（无 GNOME/Xorg/firefox/tracker/gjs）；
   - 采集前关闭 `unattended-upgrades`、`apt-daily.timer`、`snapd.refresh.timer`、`tracker-miner`、
     `packagekit`、`motd-news`，并**保持系统空闲、不要开着浏览器**；
   - 目标：攻击相关事件占比从现在的 0.3–5% 提到 **>50%**，日志体量可降一个数量级而信息量不减。
4. **每个新场景必须配 GT**（`groundtruth/<场景>.groundtruth.json`），否则无法进入
   `tools/evaluate_gt.py` 的评分流程——现有的 4/5/6 三个场景正是因为没有 GT 而无法被评估，
   这也是它们可删的实际理由之一。

---

## 7. 一句话总括

> 六个场景里，**只有场景 3 的攻击者真正出现在网络上**；
> 场景 1 是必须留的回归基线；场景 2/5/6 分别属于"同构重复""人工 busywork""根本不是攻击"；
> 场景 4 链路太短且日志被系统自动更新污染。建议删 2/5/6（可选连 4），
> 并在删之前把 Neo4j 图 dump 固化、把六库聚合结论冻结。
