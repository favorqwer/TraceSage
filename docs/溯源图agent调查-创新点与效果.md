# 溯源图 agent 自动调查：创新点、机制详解与实测效果

> 本文档记录**已经实测**的机制（含实现细节，可直接复现）与**待验证**的机制。
> 所有数字来自 `C:\Users\Favor\Desktop\pi test` 工作区的实验：
> 模型 `deepseek-flash`，六个真实多阶段攻击场景，人工标注 357 条事件边，
> 对照组为同一任务下的历史基线（边级自由探索 agent）。
>
> 评分口径：边 = `(源内容, syscall, 目标内容)` 精确三元组，同类多实例去重；
> `Process = coalesce(exepath, name)`、`File = path`、`Network = lip:lport->rip:rport`。
>
> **"平均分"一律指 macro F1**（六个场景 F1 的算术平均）；提到 micro F1 时会写明"micro"。
> 两者差别很大（E2 臂：macro 0.702 / micro 0.669），不要混用。
>
> **结构**：创新点一（步骤化表示与机械枚举，含 A/B/C 三个部件）、
> 创新点二（调查状态显式化）、创新点三（缺失感知评测），
> 加一个待验证的创新点四；末尾附“自建框架下待重试的机制”与“复现清单”。

## 创新点一：步骤化表示与机械枚举

> 本创新点由**三个部件**组成，它们共同构成一个机制，不能拆开使用：
> **A 行为步骤**（把图重组为可判断的单位）→ **B 机械枚举与伪边剔除**（让机器列边）
> → **C 步骤级因果回走**（顺着关系走）。1.4 给出三者合起来的端到端效果，1.5 给出边界。

### 1.1 部件 A · 行为步骤——把溯源图重组为"可判断、可枚举"的单位

#### 1.1.1 要解决什么问题

溯源图是几百万条零散的事件边。agent 逐条阅读有两个死结：

- **列不全**：场景 6 的 `tar` 一次调用产生 **1593 条**边，`tail` 有 **819 条**，`gzip` 有 **255 条**。
  基线 agent 全场只发 132 次查询，靠手写 Cypher 在物理上不可能列全。
- **判不出**：单条边脱离上下文看不出行为语义（"`read` 了 `/etc/passwd`"本身中性）。

#### 1.1.2 具体怎么做（可复现）

##### 步骤定义

> **一个步骤 = 一个进程实例的全部活动。**

两个要素：**归属规则 + 管道合并**。

##### （1）归属规则：每条边恰好属于一个进程

沿用「进程子图」的划分思想，按关系类型定向归属：

| 关系 | 方向 | 归属 |
|---|---|---|
| `p2f` | Process → File | **源进程** |
| `p2n` | Process → Network | **源进程** |
| `f2p` | File → Process | **目标进程** |
| `n2p` | Network → Process | **目标进程** |
| `p2p` | Process → Process | **目标进程**（子进程） |

**性质**：每条边恰好归属一个进程 ⇒ 步骤的边集互不重叠，并集 = 全图边集（划分性质）。

##### （2）取一个进程的全部自有边（三条 UNION）

```cypher
// 分支 1：本进程作为源（p2f / p2n）
MATCH (p:Process {process_id:$pid})-[e:p2f|p2n]->(x)
RETURN e.event_id AS event_id, e.starttime AS starttime, e.endtime AS endtime,
       e.syscall AS syscall, e.bytes AS bytes, 'out' AS dir, type(e) AS rel,
       coalesce(x.path, x.network_id) AS other, labels(x)[0] AS other_label
UNION ALL
// 分支 2：本进程作为目标（f2p / n2p）
MATCH (x)-[e:f2p|n2p]->(p:Process {process_id:$pid})
RETURN e.event_id AS event_id, e.starttime AS starttime, e.endtime AS endtime,
       e.syscall AS syscall, e.bytes AS bytes, 'in' AS dir, type(e) AS rel,
       coalesce(x.path, x.network_id) AS other, labels(x)[0] AS other_label
UNION ALL
// 分支 3：本进程作为子进程（p2p，归属目标）
MATCH (q:Process)-[e:p2p]->(p:Process {process_id:$pid})
RETURN e.event_id AS event_id, e.starttime AS starttime, e.endtime AS endtime,
       e.syscall AS syscall, e.bytes AS bytes, 'in' AS dir, type(e) AS rel,
       coalesce(q.exepath, q.name) AS other, 'Process' AS other_label
```

> **实现坑**：Cypher 要求 `UNION` 各分支的返回列名**完全一致**，不能只在一处写别名。

##### （3）步骤摘要字段

每个步骤对外暴露：

```
step_key, owner(内容口径), owner_args(命令行原文), t0, t1, duration_ms,
n_edges, syscalls(按次数排序的分布),
wrote_files(去重, 上限40), read_files(去重, 上限40), networks(去重, 上限20),
bytes_out, bytes_in, event_ids
```

步骤 key：`S:<process_id>:<该步骤首条边的 starttime>`
（例：`S:9330gzip:1780388651667121926`）。key 是确定性的：同一进程实例 ⇒ 同一套 key，
可跨进程、跨会话引用。

**`owner_args` 是这一创新点的关键**：命令行原文直接给出行为语义，agent 不需要猜。
实测例子（`steps.py show` 的真实输出）：

```
命令：tar -czf /root/.local/share/progql-sync/archive/sqlite_pipeline_final_20260602-162411.tar.gz
      -C /root/.local/share/progql-sync incoming work reports final
读了 797 万字节，写了 102 万字节
```

##### （4）管道合并（按需，`expand --group`）

一次管道（如 `tar -czf ... | gzip`）在图上被拆成两个进程。合并规则：

- 取步骤触及的、路径以 `pipe:[` 开头的 File 顶点；
- 查同一条管道上的**其它进程**：

```cypher
MATCH (f:File) WHERE f.path IN $pipes
MATCH (a:Process)-[w:p2f]->(f)  RETURN DISTINCT a.process_id AS pid
UNION
MATCH (f:File) WHERE f.path IN $pipes
MATCH (f)-[r:f2p]->(b:Process)  RETURN DISTINCT b.process_id AS pid
```

- 与对端进程**时间区间重叠**的步骤并入同一组。

> 不做 execve/clone 合并——**子进程是新步骤**，这是因果链的关键。

##### （5）缓存（保证确定性 + 省查询）

每个进程的边列表按 `(库, process_id)` 缓存在磁盘。同一次运行内同一进程只查一次，
因此**步骤划分结果在同一次运行内可确定性复现**。

#### 1.1.3 实测效果

**该找的边，交到 agent 手上的比例：71.1% → 94.7%**

计算方法：把 agent 每一次"展开"调用产出的三元组**按场景分别**求并集（不要跨场景合并去重，
否则会把跨场景重复的三元组吃掉，见 3.4），再与 357 条标注边求交。

| 场景 | 标注边 | 展开池里的标注边 | 池覆盖 |
|---|---|---|---|
| 1 Multi-Stage | 32 | 31 | 96.9% |
| 2 Masquerade | 32 | 31 | 96.9% |
| 3 SSH Spray | 25 | 23 | 92.0% |
| 4 Defacement | 63 | 60 | 95.2% |
| 5 Timer Hijack | 85 | 75 | 88.2% |
| 6 SQLite | 120 | 118 | 98.3% |
| **合计** | **357** | **338** | **94.7%** |

**四者对比**（同为 357 条标注边，同一评分口径）：

| 做法 | 标注边召回 | 备注 |
|---|---|---|
| **溯源引擎**（`progql-local/baseline` 最终图） | **75.6%** | micro；查准 7.7%；产物 `output/baseline/metrics-six-scenarios.json` |
| 基线 agent（边级自由探索）报告 | 71.1% | 它最后报出去的边 |
| **本机制：展开池（交到 agent 手上）** | **94.7%** | 这是**候选集**，不是报告 |
| 本机制：实际报告 | 77.0% | agent 从池里手工筛完后的结果 |

> **口径必须说清**：引擎的 75.6% 是**最终产出**，展开池的 94.7% 是**候选集**，两者不是同类量。
> 但可以得出一个有意义的结论：**本表示层交到 agent 手上的标注边，比专用溯源引擎整个最终图里含有的还多 25 个百分点。**

> **池覆盖就是本臂召回的硬上限**：agent 报不出没交给它的边。所以 94.7% 是 E2 臂的理论召回上限，
> 而它的实际报告只拿到 77.0%——**差距就是"最后一公里"丢掉的 18.6 个百分点**（详见 3.3）。
> 绝对上限（展开全部步骤、不做选择）按构造是 ≈100%，但那个做法查准只有 11.9%（见 3.3 反事实表）。

**分相位看，收益集中在"高重复、命令行语义明确"的段落**（这正是原来最弱的地方）：

| 场景 5 | 基线 | 新机制 |
|---|---|---|
| P7 归档本轮证据（`tar -czf`） | 2 / 16 | **7 / 16** |
| P6 负载哈希与压缩（`sha256sum` × 8 + `gzip -c`） | 5 / 11 | **8 / 11** |
| P3 建立 systemd 用户级持久化 | 0 / 3 | 1 / 3 |

#### 1.1.4 边界与已知问题

- **长生命周期 shell 会形成巨大步骤**：整个部署脚本可能落在一个步骤里（1593 条边）。
- 步骤的"边集"只含该进程自有边；管道对端需显式 `--group` 才会并入。

### 1.2 部件 B · 机械枚举——让机器列边，人只判边


#### 1.2.1 要解决什么问题

agent 手工枚举边的能力远不如机器：

| | 基线 agent | 机械枚举 |
|---|---|---|
| 进入报告的候选边 | 648 条（= 它最后报的） | **2834 条**（255 次展开调用，六场景合计） |
| 该找的边覆盖 | 71.1% | **94.7%** |

> **口径说明**：这两列**不是同类量**——基线那 648 是它**最后报出去的**边（它理论上能查全图，
> 只是没查），而 2834 是工具**交到它手上**的候选池。之所以仍然并排，是因为前者正是
> "agent 自己找边"能力的上界，而后者是"机器替它找边"的结果。真正可比的是
> **最终报告数**：648 → 465（见 3.3 的反事实表）。

而"把整次操作的边全倒出来"如果不做清洗，**反而比什么都不做强**：
不做过滤的全量展开平均分 **0.374**，低于基线的 **0.593**。

#### 1.2.2 具体怎么做（可复现）

##### （1）折叠：把事件实例折成"内容三元组"

**先说清它不是什么**：这一步**与 `paper/5.因果保持压缩算法` 里的任何一篇都没有关系**。
那些工作（CPR/PCAR、FDPR/SDPR、NodeMerge、SEAL、ProvGRP）做的是**图压缩**：
目标是减少存储、减少图规模，手段是事件合并、模板归约、子图聚类，并各自给出保真度指标。
本节的折叠**不是压缩算法**，它只解决一个记账问题：
**评分与报告的单位是「去重后的内容三元组」，不是事件实例**（见 `tools/eval_agent_attack_path.py`），
所以工具输出的单位必须与之对齐，否则一条读了 271 次的边会被当成 271 条边计入分母。

**它到底做了什么（用真实例子说）**

以场景 6 的 `tail -n +2 /root/.../incoming/assets.csv` 这个步骤为例，
图上有 **819 条**属于它的原始事件边。折叠后只剩 **6 条**：

| 出现次数 | 累计字节 | 源 | syscall | 目标 |
|---|---|---|---|---|
| 1 | 0 | `/usr/bin/tail` | `execve` | `/usr/bin/tail` |
| 1 | 0 | `/bin/bash` | `execve` | `/usr/bin/tail` |
| 5 | 2,516 | `/lib/x86_64-linux-gnu/libc.so.6` | `read` | `/usr/bin/tail` |
| 2 | 2,996 | `/usr/share/locale/locale.alias` | `read` | `/usr/bin/tail` |
| **271** | **2,204,927** | `.../incoming/assets.csv` | `read` | `/usr/bin/tail` |
| **539** | **2,204,894** | `/usr/bin/tail` | `write` | `.../incoming/assets_no_header.csv` |

也就是说，`assets.csv --read--> tail` 这**同一个事件重复发生了 271 次**（因为 `tail` 按块读），
在图上就是 271 条 `event_id` 不同、时间不同的边。折叠把它们并成 1 条，并保留三个东西：

- **次数**（`instances`，本例 271）；
- **累计字节**（`bytes`，本例 2,204,927 —— 正好等于该文件的完整大小，
  所以字节守恒链不会被折叠破坏）；
- **全部原始 `event_id`**（`event_ids` 数组，可回查每一次具体发生在什么时刻）。

**保留的**：源、syscall、目标、首次时间、次数、累计字节、全部实例 id。
**丢掉的**：实例之间的相对时序与每次的单独字节量（需要时用 `event_ids` 回图查）。

**折叠粒度对比**（同一个库）：

| 步骤 | 原始实例 | 折叠后三元组 |
|---|---|---|
| `gzip`（归档压缩） | 255 | **5** |
| `tar -czf ...`（打包） | 1593 | 31 |
| `tail -n +2 assets.csv` | 819 | **6** |

这一步是"高重复段落"能被处理的关键——**重复被结构性地折掉，而不是靠 agent 概括**。
（注：本例中的 `libc.so.6` / `locale.alias` 两条正是 1.2.2（2）的 R1 要剔除的对象。）

##### （2）剔除两类"结构性伪边"

这两类边的产生与实体行为无关，而是采集/建模机制造成的：

**R1 · 动态链接器对共享库的读**

```
条件：syscall == 'read' 且 src 匹配 ^/(usr/)?lib[^/]*/.*\.so(\.\d+)*$
理由：每个进程启动都要读一遍 libc / libselinux / libacl / libpcre2……
      无论进程是良性的 ls 还是攻击者的 tar，这组边完全一样
```

**R2 · 系统自带二进制的自 execve**

```
条件：syscall == 'execve' 且 src == dst
      且 src 以 /usr/bin/ /bin/ /usr/sbin/ /sbin/ /usr/lib/ /lib/ 开头
理由：execve 在图上产生两条边，其中"可执行文件 → 子进程"这条在内容口径下，
      当文件路径与进程内容同名时就成了自环（/usr/bin/cp --execve--> /usr/bin/cp）。
      这是内容口径的产物，不是"cp 执行了 cp"。
```

**明确不剔除的东西**（防止过度精简，每一条都有反例）：

| 不剔除 | 反例（在标注里真实存在） |
|---|---|
| 不按目录前缀剔除 `/proc/` `/sys/` `/dev/` | `/proc/cpuinfo --read--> /usr/bin/cp`、`/dev/zero --read--> /usr/bin/dd`（场景 5 的核心边） |
| 不剔除整个 `/usr/lib/` | `/usr/lib/openssh/sftp-server`、`/usr/lib/systemd/systemd`（场景 4/5 的关键进程） |
| 不剔除所有自 execve | `/tmp/.system_service.sh --execve--> /tmp/.system_service.sh`（场景 1，攻击者脚本） |
| 不剔除零字节的读写 | 标注里存在 0 字节边 |
| 不剔除 `fcntl` | 口径上它只产生 `n2p` 边，保留不影响 |

> **这里曾有一小节叫"公平性披露"，已移出本创新点**——它确实**不是机制**，
> 而是论文写作时要交代的方法学内容，现已并入 [3.5 论文写作必须交代的三段](#35-论文写作必须交代的三段不是机制)。
> 把它摆在"部件 B 的实现步骤"里是分类错误，感谢指出。

#### 1.2.3 实测效果

| 指标 | 基线 | 新机制 |
|---|---|---|
| 工具交到手上的候选三元组 | —（无此机制） | **2834 条**（255 次展开调用，六场景合计） |
| 自 execve 假边 | 36 条 | **0 条** |
| 报告里名字写错的边 | **77 处** | **0 处** |

**"77 → 0"是本创新点最硬的证据**：两个新臂共 12 个"场景 × 臂"组合，
**event_id 全部能在库中查到、端点内容与 syscall 全部与库内一致，零错误。**

（基线那 77 处的具体形态：把 `/bin/bash` 写成 `bash`、`/usr/bin/cp` 写成 `cp`，
直接导致无法与标注对齐。E2 臂的边直接来自工具输出，M1 臂的内容来自状态图登记，两者都无法写错。）

#### 1.2.4 边界与已知问题

- **过滤对"候选池"是必要的，对"最终报告"不是承重的**：
  三个臂的报告里**都没有**动态库读——说明基线 agent 自己也会避开这类噪声。
  R1 的价值在池层面（避免池被 libc 读撑爆），R2 的价值在报告层面（清掉 36 条自环）。
- 折叠后 `bytes` 是**该三元组所有实例的字节合计**，`event_ids` 保留全部实例 id 以便回查。

### 1.3 部件 C · 步骤级因果回走——顺着关系走，而不是猜下一步查什么


#### 1.3.1 要解决什么问题

反向追踪的每一步都要回答"上一步是什么"。如果让 agent 自己猜该查什么，它会反复试错、
发大量查询、且容易漏掉整条分支。

#### 1.3.2 具体怎么做（可复现）

给定一个步骤 `S`（进程 `P`，时间区间 `[t0, t1]`），工具返回**四类前驱候选**，每条都带理由：

##### 类型 1 · 派生父：谁启动了这个进程

```cypher
MATCH (q:Process)-[e:p2p]->(p:Process {process_id:$pid})
WHERE e.starttime <= $t1
RETURN q.process_id AS qpid, coalesce(q.exepath,q.name) AS qname,
       e.starttime AS t, e.event_id AS eid, e.syscall AS sc
ORDER BY e.starttime DESC LIMIT 10
```

理由字段：`以 <syscall> 派生本进程（<父进程内容>）`

##### 类型 2 · 管道对端：同一条管道的另一端

见创新点一（4）的查询。理由字段：`同一条管道的另一端`

##### 类型 3 · 文件来源：本步骤读的文件，之前是谁写的

```cypher
MATCH (pw:Process)-[w:p2f {syscall:'write'}]->(f:File)
WHERE f.path IN $paths AND w.starttime <= $t0
RETURN f.path AS path, pw.process_id AS qpid, coalesce(pw.exepath,pw.name) AS qname,
       w.starttime AS t, w.event_id AS eid
ORDER BY w.starttime DESC
```

- 每个文件取**最近的一个写入者**；
- `$paths` = 本步骤读取的文件（排除 `pipe:[` / `unix:[`），按读取字节量取前若干个。

理由字段：`<路径> 的上一个写入者（<进程内容>）`

##### 类型 4 · 网络对端：本步骤触及的网络端点上，之前还有谁

```cypher
MATCH (p:Process)-[e:p2n]->(n:Network)
WHERE n.network_id IN $nets AND e.starttime <= $t1
RETURN n.network_id AS nid, p.process_id AS qpid, coalesce(p.exepath,p.name) AS qname,
       e.starttime AS t, e.event_id AS eid
ORDER BY e.starttime DESC
```

理由字段：`同一 Network 端点 <network_id> 上的活动（<进程内容>）`

##### 输出

每条候选解析成**步骤 key + 该步骤的摘要**，因此 agent 拿到的是
"下一个该看的操作 + 它的命令行原文 + 它的边数"，而不是一堆裸 id。

**实测输出示例**（`steps.py preds` 的真实结果，从 POI 的 `gzip` 步骤出发）：

```json
{"reason":"spawn","process_content":"/bin/sh","process_args":"-c gzip",
 "step_key":"S:9329sh:1780388651666567215","step_n_edges":7}
{"reason":"pipe","process_content":"/usr/bin/tar",
 "process_args":"-czf /root/.../sqlite_pipeline_final_20260602-162411.tar.gz -C ... incoming work reports final",
 "step_key":"S:9328tar:1780388651665357758","step_n_edges":1593}
```

**一次调用就从归档进程走到了打包进程，而且命令行原文直接给出了这次操作干了什么。**

#### 1.3.3 实测效果（用大白话说）

**这个工具到底干什么**：往回走的时候，每一步都要回答"上一步是什么"。
没有它，agent 只能自己猜"我接下来该查哪个进程/哪个文件"，猜错了就白花一轮。
有它，工具直接给出四个方向的候选（谁启动了这个进程 / 同一条管道的另一端 /
这个文件的上一个写入者 / 同一个网络端点上还有谁），**agent 只需要点头或摇头**。

**它干得好不好**（重放那 29 次调用算出来的，重放是确定性的）：

- 工具一共给出 **48 个"下一步该看的地方"**。
- 这 48 个里，**35 个（73%）确实是攻击链上的步骤**。
  → 也就是说，**工具指的方向基本是对的，很少带偏路**。
- agent 采纳了其中 **73%**（48 个里有 13 个它看到了但没去看）。
- 但最终报告里的边，只有 **16%** 来自这些"工具指过的步骤"（475 条里 76 条，其中 69 条命中）。

**所以结论是**：

| 问题 | 答案 |
|---|---|
| 它准不准？ | **准**。它指的方向 73% 是攻击链上的。 |
| 它重要吗？ | **不是主力**。最终报告里只有 16% 的边来自它指的地方。 |
| 它有什么用？ | **省试错**。agent 不用猜下一个该查什么，跟着指针走就行。 |
| 它提高了召回吗？ | **没有直接证据**。因为没有"不用它"的对照臂，它的收益无法与 A/B 分开归因。 |

**它的边界（已知）**：只能往回走。"从 POI 往前"的分支它看不到——详见 1.3.4。

#### 1.3.4 边界与已知问题（重要）

> **本机制只往回走，结构性地覆盖不到"从 POI 往前"的分支。**

下面是把六场景每一条标注边按"实例时间是否全在 POI 之后"分类的完整结果
（POI 时间取自报告里登记的 `poi.event_ids`；产物可用 `tmp/` 下的重算脚本重现）：

| 场景 | POI（UTC） | 标注边 | **完全在 POI 之后** | 具体在哪 |
|---|---|---|---|---|
| 1 Multi-Stage | 08:50:45 | 32 | **0** | POI 就是最后一步 |
| 2 Masquerade | 14:49:23 | 32 | **0** | POI 就是最后一步 |
| 3 SSH Spray | 08:11:42 | 32 | **4** | P8 会话心跳（`printf` 写 `activity.log`）1 条；P9 尾部失败爆破（`Kali:41552` 的 `accept`）3 条 |
| 4 Defacement | 13:17:27 | 93 | **15** | P9 篡改结果网络回显（Kali curl 抓被篡改首页与标记文件）7 条；P10 投递包归档 5 条；P1 会话建立里 3 条 |
| 5 Timer Hijack | 08:04:03 | 88 | **3** | P7 归档相位内、POI 之后的 3 条 |
| 6 SQLite | 08:24:11 | 130 | **10** | P7 第二次同步（与首轮同签名，仅列差异边）8 条；P6 内 POI 之后 2 条 |
| **合计** | — | **357** | **32（7.9%）** | — |

**除了"POI 之后"，还有一类"POI 之前但不在回溯路上"**：

场景 4 的 **P0 站点基线抓取**（15 条边）——攻击者**自己**在改站前先 curl 了一遍网站留底。
它在时间上早于 POI，但它是**另一条分支**：它和主链唯一的连接是
`/srv/progql-web/current/*.html --sendfile--> /usr/sbin/nginx`（也就是 POI 所在相位写下的文件
**后来**被 nginx 读）。所以从 POI 往回走永远碰不到它。

**这条边要"从这个文件往前看"才找得到**（"我写的这个文件，后来被谁读了？"），**不是往回看**。

这一点**标注文件自己也承认**：GT 修订记录里写着「孤岛补边：补 5 条把两处弱连通分量接回主链」，
补的正是这些 `sendfile` 边——**在补这几条边之前，网站那一支在图上跟主链不连通。**

**把两类加起来**：场景 4 有 15（P0）+ 15（P9/P10/P1）= **30 条 / 原 93 条 = 32%** 的标注边
**根本不在"从 POI 往回走"的路径上**——**这 30 条现已全部从 GT 删除**（见"评测范围修正"一节），
场景 4 的标注边从 **93 降到 63**（9 个相位）。

**删掉它们之后的实测**：步骤机制在场景 4 回退 **8%**（0.711 → 0.657）；
状态显式化反而提升 **9%**（0.776，该场景最好的臂）。
**即"反向追踪范式覆盖不到网站侧分支"对步骤机制是实打实的损失，对状态显式化则被"少而准"的取舍抵掉了。**
M1 臂的会话里 `nginx` 出现 **0 次**——它压根没往那个方向看（对照：基线 98 次、E2 200 次）。
（`:8081` 的提及次数不能作此判据：M1 会话里仍出现 71 次，因为它在扫端口时看到过该端点，
只是从未把 `nginx` 这条线展开；基线 215 次、E2 143 次。）

**需要的补丁**（见待验证创新点四）：
① 加"往前看"的查询；② 加"空白区审计"。

## 创新点二：调查状态显式化——把"确认了什么 / 假设了什么 / 查不到什么"变成一等公民

> **定位说明（必读）**：本臂实测表明，状态图**在本实验中没有参与在线推理**——
> agent 对 `state.py context` 的调用是 **0 次**，也从未调用 `set-status`。
> 它的实际角色是**事后的可审计输出产物**（把结论、假设、缺口显式登记成可核对的清单），
> 而不是"边查边读"的推理基质，更不是省上下文的成本机制（实测上下文 **+34.9%**）。
> 因此本创新点的主张是**可审计性与报告保真度**，不是推理机制、也不是成本机制。详见 2.3、2.4。


### 2.1 要解决什么问题

基线 agent 的调查进展只存在于对话文本里。三个后果：

- **不可查询**：无法问"当初为什么排除 B"；
- **不可审计**：最终报告里没有任何东西说明"哪些结论有依据、哪些没有"；
- **无法表达"缺失"**：图上查不到东西时，报告里只有几句笼统的"不确定项"。

### 2.2 具体怎么做（可复现）

#### （1）三类节点

| 类型 | 含义 | 状态取值 |
|---|---|---|
| `entity` | 图上的一个实体（Process / File / Network / **Step**） | `unexplored` / `tracing` / `confirmed` / `excluded` |
| `hypothesis` | 一条攻击假设（如"存在用户级 systemd 持久化"） | 同上 |
| `gap` | **待证缺口**："这里应该有边但图里查不到" | `open` / `closed` |

#### （2）四类边

| 关系 | 含义 |
|---|---|
| `supports` | 该证据支持该假设 |
| `refutes` | 该证据反驳该假设 |
| `derived-from` | 该结论由另一结论推出 |
| `in-step` | 实体属于某个步骤 |

#### （3）键的构造（确定性、可复用）

```
entity(Process)  →  proc:<coalesce(exepath,name)>
entity(File)     →  file:<path>
entity(Network)  →  net:<lip:lport->rip:rport>
entity(Step)     →  step:<S:process_id:start_ns>
hypothesis       →  调用方指定，如 H:S4-deploy
gap              →  gap:<sha1(label)[:10]>   （未指定 key 时自动生成）
```

#### （4）存储

本地 SQLite，**不写证据库**（证据不可变是整套方法学的前提）：

```sql
CREATE TABLE nodes (
  key TEXT PRIMARY KEY, kind TEXT NOT NULL, label TEXT, status TEXT,
  etype TEXT, payload TEXT, seq INTEGER, created REAL, updated REAL);
CREATE TABLE edges (
  id INTEGER PRIMARY KEY AUTOINCREMENT, src TEXT NOT NULL, rel TEXT NOT NULL,
  dst TEXT NOT NULL, note TEXT, payload TEXT, seq INTEGER, created REAL,
  UNIQUE(src, rel, dst, note));
```

`seq` 是单调递增序号，因此**调查的先后顺序可还原**（用于事后分析调查行为）。

#### （5）上下文渲染

```
state.py context [--key K ...] [--kind hypothesis] [--status confirmed] [--limit N]
```

输出为紧凑的文本块：每个节点一行（类型 / 键 / 状态 / 标签），其下缩进列出关联边与备注。

> **实测重要修正**：本臂的 agent **从未调用过这个命令**（`state.py context` 调用 **0 次**）。
> 它只用了 `snapshot`（7 次）、`stats`（2 次）、`list`（2 次）做收尾导出。
> 因此**"agent 用状态图回顾进展"这件事在本实验中并未发生**——状态图是**事后的登记产物**，
> 不是在线推理的上下文来源。该命令仍然有用（人工核对、跨会话恢复），但不能拿来当机制证据。

#### （6）命令集

```
add-entity      --spec-json '{"content":"/usr/bin/gzip","etype":"Process","status":"confirmed"}'
add-hypothesis  --key H:archive --label "归档管道是攻击链末段"
add-gap         --label "sha256sum 校验读边在图上缺失"
link            --src <key> --rel supports --dst <key> --note "..."
set-status      --key <key> --status confirmed
context / list / get / neighbors / stats / snapshot
```

> **实现坑（Windows/Git Bash）**：MSYS 会把以 `/` 开头的命令行参数改写成
> `C:/Program Files/Git/...`。所以路径类内容必须走 `--spec-json`（JSON 以 `{` 开头，不会被改写）。

### 2.4 边界与已知问题

- **定位必须是"可审计输出 / 报告保真度"，不能写成"推理机制"，更不能写成"成本机制"。**

  **证据 1 —— 它没参与推理**：`state.py context` 调用 **0 次**，`set-status` 调用 **0 次**。
  实际流程是：先用原始 Cypher 探索 → 写叙事 `narrN.md` → **事后**写脚本
  `scratch/state_s1..6.sh` 把结论批量登记进状态图 → 用 `mkstate.py` 按场景切分。
  也就是说，状态图是**事后的输出格式**，不是"边查边读"的基质。
  真正起作用的是"**必须逐条把实体抄进脚本**"这个强制核对动作（这正好解释了内容错误 77 → 0）。

  **证据 2 —— 它不省成本**：峰值上下文 **+34.9%**（311,415 → 420,148 token）。
  原因有两层：① agent 框架**没有"忘记"功能**，外部状态只能往对话上再加一层，替不掉对话；
  ② 本臂实际**多拉了 23% 的原始数据**——工具结果从基线的 151,807 token 当量升到 **186,541**，
  并把 28 个原始查询结果 dump 到 `scratch/*.json`（合计 **896 KB**）。
  工具往返次数也从 173 增到 196。

- **协议未收尾**：26 条假设**全部停留在 `tracing`**，21 条缺口**全部 `open`**，`set-status` 调用 0 次。
  登记做了，收尾没做——这与"状态图未被读回"是同一个原因。
- **广度损失**：场景 4 掉了 13%，整块网站侧没查（见 1.3.4）。

### 2.5 它到底算不算"对溯源的提升"？（直接回答）

**分三层回答，不要混为一谈：**

**（1）数字上，本臂确实比基线强很多**：平均分 **0.593 → 0.783（1.32×）**，
查准 **39.2% → 83.2%**，场景 3/5 各 **2.30×**。所以**不能说"对溯源没有提升"**。

**（2）但提升的**归因**不成立**：本臂的 agent **从未读回状态图**（`context` 0 次、`set-status` 0 次），
所以"状态图帮我理清了思路"这个因果链在本实验里**没有被建立**。
实际发生的是：agent 先用原始 Cypher 探索完，再事后把结论批量登记。

**（3）那提升从哪来？** 两个可证伪的候选解释，尚未分离：

| 候选解释 | 支持证据 | 如何分离（待做） |
|---|---|---|
| **强制核对**：登记实体时必须逐条把内容抄进脚本，因此内容错误 **77 → 0** | 77→0 是实测；两个臂都有这个效果 | 对照臂：只要求"报告实体内容必须从图复制"，不要求建状态图 |
| **保守化**：本臂的提示词强调"不确定就登记为缺口"，导致报的边少了 55% | 报边 648→291（少 55%），命中只少 9% | 对照臂：同样提示"保守报告"，但不给状态图工具 |

**结论**：

- ✅ **作为可审计产物**：成立，且是本工作最有价值的产出之一（**21 条自动发现的图缺陷** + 报告零内容错误 +
  实体清单可核对 80.7% 的标注端点）。这部分**不需要"参与推理"就能成立**。
- ⚠️ **作为"提升溯源准确率的机制"**：**尚无证据**。要坐实它，必须先让状态图真的被读回
  （见"自建框架下待重试的机制"第 2 条的未来设计）。
- ❌ **作为成本机制**：不成立（+34.9%）。

## 创新点三：缺失感知的评测方法——区分"没找到"与"图上没有"

> **定位说明（先说清它是什么、不是什么）**：
> 这**确实不是一个系统机制**，而是一套**评测方法**。把它列为创新点，理由只有一个：
> **它推翻了一个错误结论，并且给出了一个可行动的方向。**
>
> 具体地：如果只用常规口径（报告 vs 标注），E2 臂的结论会是
> "平均分从 0.593 提到 0.702，提升有限，表示层没用"——**这是错的**。
> 本方法把"表示层问题"与"选择问题"分开之后，才看到真相：
> **表示层已经把 94.7% 的真边交到了 agent 手上（比专用引擎的整个最终图还多 25 个百分点），
> 是 agent 在最后一步丢掉了 18.6 个百分点。**
> 这直接把优化目标从"换表示"改成了"改选择机制"。
>
> **如果评审不接受"评测方法算创新点"**，本方法应降级为评测章节的一节，
> 而论文的创新点只剩两个（步骤化表示 + 状态显式化）——这也是一个诚实且站得住的写法。


### 3.1 要解决什么问题

现有 LLM 溯源调查的评测把两件事混为一谈：

- **agent 没找到**（方法问题）；
- **图上根本没有**（采集/建模问题）。

混在一起，召回数字就不可解释。而且没人知道"表示层到底把多少真边交到了 agent 手上"，
"agent 又丢掉了多少"——**瓶颈到底在哪一层，无从判断**。

### 3.2 具体怎么做（可复现）

#### （1）把标注边解析回图

标注只有 `(源内容, syscall, 目标内容)`，没有时间、没有 event_id，需要解析成图上实例：

**第一步：按端点内容推断关系类型**

```
两端都是进程内容            → p2p
源是进程、目标是 IP:port     → p2n
源是 IP:port、目标是进程     → n2p
源是进程、目标不是          → p2f
目标是进程、源不是          → f2p
```

**第二步：回退到该 syscall 可能对应的全部关系类型**

```python
SYSCALL_REL = {
  'execve': ('p2p','f2p'), 'clone': ('p2p',),
  'read': ('f2p','n2p'),   'recvfrom': ('f2p','n2p'),
  'accept': ('n2p',),      'fcntl': ('n2p',),
  'write': ('p2f','p2n'),  'sendto': ('p2f','p2n'),
  'connect': ('p2n',),     'bind': ('p2n',),
  'rename': ('p2f','f2p'), 'unlink': ('p2f','f2p'), 'mkdir': ('p2f','f2p'),
  'chmod': ('p2f','f2p'),  'symlink': ('p2f','f2p'),
  'sendfile': ('f2p','p2f','p2n'),
}
# 先查推断出的类型，再查该 syscall 的其它候选类型，结果按 event_id 去重合并
```

**这一步是必须的**：像 `/usr/bin/mv`、`/tmp/xxx.sh` 这类端点**既是进程内容又是文件路径**，
单靠内容推断会判错方向。回退查询保证不会误判成"图上没有这条边"。

**第三步：走索引查询**（性能关键）

```cypher
-- p2f：从进程侧进，用 process_id 索引，再按 file_id 过滤
MATCH (p:Process)-[e:p2f]->(f:File {file_id:$dst})
WHERE e.syscall = $sc AND p.process_id IN $pids
  AND e.starttime >= $a AND e.starttime <= $b
RETURN e.event_id AS event_id, e.starttime AS starttime,
       p.process_id AS owner_pid, 'p2f' AS rel LIMIT $n
```

- `File.file_id` 与 `File.path` **恒等**（实测 mismatch = 0），所以可以走唯一约束索引；
- `Process` 按 `process_id` 索引；`Network` 按 `network_id` 索引；
- 用场景的采集时间窗过滤，避免全表扫描。

**第四步：owner 从实际边取，不从推断取**

- `p2f` / `p2n` → owner = 源进程
- `f2p` / `n2p` → owner = 目标进程
- `p2p` → owner = 目标进程（子进程）

**校验**：把推断出的关系类型与解析出的实际关系类型比对。
六场景实测 130/130、93/93、32/32、32/32、85/88、28/32 ——
**不一致的 3 条都是"端点既是进程又是文件"的情形，而 owner 全部正确**（因为 owner 取自实际边）。

#### （2）把标注边映射到步骤

```
标注实例 (owner_pid, starttime) → 该进程在该时刻所属的步骤
```

#### （3）两个关键指标

| 指标 | 含义 | 怎么算 |
|---|---|---|
| **池覆盖** | 表示层把多少真边**交到 agent 手上** | agent 全部展开输出的三元组并集 ∩ 标注边 |
| **报了池里的多少** | agent 在最后一步**丢掉了多少** | 报告三元组 ∩ 标注边 ÷ 池覆盖 |

这两个数把"表示层问题"和"选择问题"彻底分开。

#### （4）可达上限（把"表示能做到多好"和"agent 能做到多好"分开）

对候选步骤集合做**贪心最大化 F1**，扫 k 出 Pareto 曲线：

```
候选 = 标注边所在的步骤（两个版本：只含 agent 触及过的 / 全部）
对每个步骤算它的三元组集合
每轮：加入使 F1 最大的那个步骤，记录 (k, 精确率, 召回率, F1)
```

**这个数字用到了标注做选择，所以它是"可达上限"，不是"agent 会拿到的分"。**
它的作用是回答：**如果 agent 选得完美，能到多少？**

### 3.3 实测效果

**（a）标注边在图上的存在性：357/357 全部存在**（六个场景逐条解析，无一条缺失）。
→ 说明召回缺口不是图缺失造成的，可以放心把召回当作方法指标。

**（b）可达上限 vs 实际，定位出瓶颈：**

| | 平均分（macro F1） |
|---|---|
| 基线（自由探索） | 0.593 |
| 全量展开（不做选择） | 0.374 |
| 全量展开 + R1/R2（并集，不做选择） | 0.559 |
| **最优筛选步骤 + 过滤（可达上限）** | **0.797** |
| 新机制实际拿到（E2 臂） | 0.702 |

**（c）决定性诊断：表示层成功了，最后一公里丢了**

| 场景 | 标注边 | 池覆盖 | 池覆盖率 | 报告命中 | 报了池里的 |
|---|---|---|---|---|---|
| 1 | 32 | 31 | 96.9% | 31 | 100.0% |
| 2 | 32 | 31 | 96.9% | 31 | 100.0% |
| 3 | 25 | 23 | 92.0% | 22 | 95.7% |
| 4 | 63 | 60 | 95.2% | 45 | **75.0%** |
| 5 | 85 | 75 | 88.2% | 58 | 77.3% |
| 6 | 120 | 118 | 98.3% | 88 | 74.6% |
| **合计** | **357** | **338** | **94.7%** | **275** | **81.4%** |

**结论：表示层把 94.7% 的真边交到了 agent 手上，agent 在最后一步丢掉了 18.6%。**
**瓶颈从"找得到"转移到了"报得全"。** 这个结论靠本评测方法才能得出。

**（d）反事实模拟（把"没执行的机制"补上会怎样）**

下面是四种"报告该报什么"的对照。**注意区分 micro 与 macro**：

| 做法 | 报告三元组 | 命中 | 召回 | 查准 | micro F1 | **平均分（macro）** |
|---|---|---|---|---|---|---|
| 基线（自由探索） | 648 | 254 | 71.1% | 39.2% | 0.505 | 0.593 |
| **实际发生**（agent 手工筛过） | 465 | 275 | 77.0% | 59.1% | 0.669 | **0.702** |
| 把整个展开池当报告 | 2834 | 338 | 94.7% | 11.9% | 0.212 | 0.379 |
| 把标记"要"的 245 个操作全量倒出 | 2092 | 317 | 88.8% | 15.2% | 0.259 | 0.393 |

**结论：真按协议做会更差**——把选中操作全量倒出，平均分从 0.702 掉到 **0.393**（低于基线的 0.593）。
原因：agent 把 245 次操作标了"要"、**0 次标"不要"**，另有 209 次展开过但未登记，
它没有能力挑出该要的那二三十个。**它的手工筛边不是违规，而是在补救自己的选择无能。**

> 早期版本把"把整个展开池当报告"的 micro F1 误写成了"平均分"，并与基线的 micro F1（0.505）
> 比较。上表已把 micro 与 macro 分开。

### 3.4 边界与已知问题

- **可达上限用了标注做选择**，是"可达"不是"会拿到"。
- **`step_recall`（步骤覆盖率）这个指标没有诊断价值**：
  标注边在步骤间高度重复，导致它是个数百分比（场景 3 只有 3.4%），
  却对应 93.8% 的边级覆盖。**判断一律看边级 F1 和可达上限，不要看它。**
- 反事实模拟是从日志重算的估计值，不是实跑结果。
- **池覆盖与"报了池里的多少"必须逐场景算**：把所有场景的展开池合并去重会跨场景吃掉重复三元组
  （六场景合计从 2834 降到 2630），得到的是错的数。

### 3.5 论文写作必须交代的三段（**不是机制**）

> 这三段**不是创新点**，但审稿一定会问，必须写进论文的评测/局限章节。
> （之前把第一段摆在"部件 B 的实现步骤"里，是分类错误，已改正。）

**（1）过滤规则 R1/R2 的来源与公平性**

- R1/R2 的**动机不依赖标注**：一条来自动态链接器的行为常识，一条来自"f2p execve 自环是内容口径产物"。
- 定稿前**核对过它们是否会删掉标注边**：结果是 **0 条**（六场景 357 条全部安全；407 时亦为 0 条）。
  这是必要的一致性检查，不是调参。
- 因此同时给出**未加过滤**与**加过滤**两组数字，读者可自行判断增益来自哪一部分：

| 做法 | 平均分 |
|---|---|
| 基线（自由探索） | 0.593 |
| 全量展开、不过滤 | 0.374 |
| 全量展开 + 过滤（并集，不做选择） | 0.559 |
| **最优筛选步骤 + 过滤（可达上限）** | **0.797** |

**结论**：过滤不是提高成绩的原因（0.559 仍低于基线），
而是**让"全量展开"不帮倒忙的保险**；增益来自"步骤粒度 + 选择 + 机械枚举"这个组合。

**（2）micro 与 macro 必须分开写**

- "平均分"一律指 **macro F1**（六场景 F1 的算术平均）；提到 micro F1 时必须写明。
- 两者差别很大（E2 臂：macro 0.702 / micro 0.669），混用会让读者算错。

**（3）评测范围：GT 里混入了 POI 之后的边**（详见下面独立一节）

本工作的任务是**反向追踪**（从 POI 往回找入口），但标注里同时包含了
**POI 之后**的攻防活动。这对所有后向方法都不公平。详见下一节。

## 待验证创新点四：机器粗筛 + agent 细判


### 4.1 主张

> **粗的筛选交给机器（用不需要标注的死规矩），细的判断交给 agent。**

### 4.2 为什么这么设计（有实测依据）

数据揭示了一个**反直觉**的事实：

> **agent 能一条一条看边，判断"这条边可疑不可疑"（它的手工筛选把平均分从 0.379 救到 0.702）。
> 但它看不了"一整次操作"（它把 245 次操作标了"要"、0 次标"不要"）。**

这与设计时的假设正好相反。原设计假设"粗的判断更容易"（判断"这次打包要不要"比判断 49 条边容易），
**实测是反的**：边级别它有具体内容可抓（路径、syscall、字节数），
操作级别它只拿到一堆汇总，而"这一整次操作算不算攻击"本身就很模糊——
**尤其是它已经从 POI 往回追到的操作，每一个都"看起来跟攻击有关"**，所以它没有理由排除任何一个。

### 4.3 候选粗筛规则（不需要标注，可计算）

- **新端点规则**：这次操作是否引入了之前没出现过的文件路径 / 网络端点？
- **稀有度规则**：这条命令行在这个进程身上出现过几次？（越少见越可疑）
- **因果距离规则**：这次操作离 POI 的因果跳数。
- **结构位置规则**：这次操作是否在 POI 的反向可达集内，且不是纯噪声 syscall 组合。

### 4.4 怎么验证（不用跑 agent）

```
1. 用上述规则给"标注边所在的步骤"和"其它步骤"打分，看分离度（AUC 之类）。
2. 只保留分数最高的 k 个步骤，全量倒出它们的边，算平均分。
3. 与"可达上限 0.797"和"基线 0.593"对比。
```

### 4.5 判死条件

- 若规则筛完之后能达到的最高分 **< 0.65**（比基线 0.593 没强多少）→ 这条路判死。
- 若规则筛出的步骤里**绝大多数与攻击无关**（比如筛 1000 个只有 2 个有用）→ 等于把噪声推给 agent，判死。

### 4.6 同时要补的两个零件（针对创新点一 1.3.4 的边界）

| 零件 | 解决什么 | 怎么验 |
|---|---|---|
| **往前看查询**：「我写的这个文件，后来被谁读了？」「这个地址后来还有谁碰过？」 | 场景 4 丢失的网站侧分支（`File --sendfile--> nginx`） | 要跑一次 agent |
| **空白区审计**：「这个时间窗里，图上有哪些进程/端口，是我还没登记过的？」 | 缺口清单只能记"注意到的缺失"，记不了"没去看" | **不用跑 agent**，直接查图 |

## 在现成框架下失败、但在**自建 agent 架构**下可能成立的机制

> 本节记两个**在现成 pi 框架下不成立**的机制。
> 它们失败的原因**不是想法错，而是现成框架不提供必需的条件**。
> 后面会自建 agent 架构，因此把「需要什么条件、怎么设计、怎么验证」写清楚，作为后续工作清单。
>
> （另有一条已判死的机制——“让 agent 自己挑哪些操作算攻击”——已并入
> [待验证创新点四 4.2](#42-为什么这么设计有实测依据)，不在此重复。）

### 1. 用外部状态替掉对话历史（"省对话长度"）

**现成框架下为什么失败**

- pi 框架**没有"忘记"功能**：从头到尾携带全部对话历史，外部状态只能往对话上**再加一层**，
  替不掉任何东西。实测峰值上下文 **+34.9%**（311,415 → 420,148 token）。
- 更具体地说，它**多拉了 23% 的原始数据**：工具结果 151,807 → 186,541 token 当量，
  并落盘 28 个 `scratch/*.json` 合计 896 KB。所以就算不看状态图，它也已经比基线更贵。
- 根据预检 B：基线上下文里 **75.4%** 是**可重建**的原始查询结果，M1 臂是 **79.3%**。
  也就是说，**大部分上下文都是"可以扔掉、需要时再查"的东西**——这正是本机制的机会。

**自建框架下怎么让它成立**

需要的条件是：**agent 的上下文可以被显式裁剪**。具体设计：

1. 上下文 = `系统提示 + 状态图快照（紧凑文本） + 最近 K 轮工具结果`；
2. 超过 K 轮的工具结果**直接从上下文里丢弃**，但丢弃前必须先把它们蒸馏成状态图节点
   （实体 / 假设 / 缺口），否则就真的丢了；
3. 需要旧数据时，用 `state.py context` / `get` 重新取回（这时状态图才真正"替掉"了对话）；
4. 关键约束：**状态图必须是跨场景、跨阶段的唯一记忆**，不得依赖对话携带结论。

**怎么验证（可量化）**

- 主指标：**峰值上下文**。目标：从 311,415 token 降到 **≤125,000（−60%）**。
  依据：可重建部分占 75%，把这部分换成按需查询就是理论上限。
- 副指标：**同一 macro F1**（不得低于基线的 95%）；
  `context` 调用次数应当与轮次同阶（而不是 0）；状态写入量不得反而上升。
- 判死条件：峰值上下文没降，或 F1 掉到基线的 90% 以下。

### 2. 把状态图当"在线推理基质"

**现成框架下为什么失败**

- 本臂 agent **从未读回状态图**：`state.py context` **0 次**、`set-status` **0 次**。
  它是"先探索 → 写叙事 → 事后批量登记"（`scratch/state_s1..6.sh`），
  结果 26 条假设全 `tracing`、21 条缺口全 `open`。
- **根本原因**：在现成框架里，状态图只是**又一个可选工具**。
  对 agent 来说，"把结论写在回复里"与"把结论写进状态图"成本一样、后者更麻烦，
  所以它会选择前者，把状态图当**收尾作业**。
- **教训**：**工具的可用性 ≠ 工具会被使用**。想让状态图参与推理，必须把它变成**硬约束**，而不是可选动作。

**自建框架下怎么让它成立**

1. **硬约束读回**：每进入一个新探索方向前，必须先输出一次 `context`；
   不输出则工具层拒绝后续查询（可以在自建框架里把这条写进控制循环）。
2. **硬约束收尾**：任何一条 `hypothesis` 不得在 `tracing` 状态下离开该场景——
   必须变成 `confirmed`（附证据边）或 `excluded`（附反证），否则不允许写报告。
3. **硬约束缺口**：每条 `gap` 必须带一个"下次该怎么查"的具体动作（哪个库、哪条 Cypher），
   而不是只记一句"图上没有"。
4. **状态图作为唯一跨场景记忆**（与上一条机制共用）。

**怎么验证（可量化，不需标注）**

| 指标 | 现成框架实测 | 目标 |
|---|---|---|
| `context` 调用次数 | **0** | ≥ 轮次的 30% |
| `set-status` 调用次数 | **0** | ≥ 假设数 |
| 假设收尾率（非 `tracing`） | **0 / 26** | ≥ 90% |
| 缺口关闭率 | **0 / 21** | 报告里每条缺口都有后继动作 |
| 矛盾率（后续相位推翻前面结论的次数） | 未测 | 降低 |

- 主指标：**矛盾率**与**假设收尾率**——这两个才是"状态图真的参与推理"的间接证据。
- 判死条件：`context` 调用仍为 0，或收尾率上不去（说明 agent 只是在应付约束）。

### 3. 两条机制的共同前提

这两条都指向同一个前提：**自建框架必须能把"上下文管理"与"控制循环"纳入自己的管辖**。
具体要能控制三件事：

1. **裁剪上下文**（丢掉旧工具结果）；
2. **强制插入工具调用**（把"先读状态"变成不可跳过的一步）；
3. **拒绝不合规的输出**（假设未收尾就不让写报告）。

现成框架三件都不给，所以只能做"可审计产物"；自建后这三条都能做到，机制才有机会变成真正的推理机制。

| `tools/check_run.py` | 跑完后的合规校验（齐全性/格式/真实性/臂约束/越界） |
| `tools/finish_run.py` | 一键收尾：合规 + 评分 + 上下文成本 + 与基线对比 |
| `tools/set_arm.py` | 切换实验臂（防呆：arm 名校验、run_id 复用拒绝） |
| `analysis/common.py` | 标注口径、图内解析、步骤映射、贪心可达上限 |
| `analysis/precheck_A_steps.py` | 可达上限与池覆盖计算（不需要跑 agent） |
| `analysis/precheck_B_context.py` | 从会话日志分析上下文构成 |
| `analysis/score.py` | 任意 run 的评分 + 行为指标 |
| `analysis/FILTER-PREREG.md` | R1/R2 过滤规则登记（实验前固定，不得中途修改） |

### 关键参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| 每进程边数上限 | 200000 | 超过则警告，划分可能不完整 |
| `--max-rows`（q.py） | 1000 | 单次查询返回上限 |
| 折叠后的 `wrote_files` / `read_files` / `networks` | 40 / 40 / 20 | 步骤摘要的展示上限 |
| 前驱查询的 `LIMIT` | 10（spawn）/ 5（网络） | 候选数量上限 |

### 运行协议

每个实验臂：改 `run.json`（`run_id` + `arm`）→ 开新 agent 会话 → 完成后跑 `finish_run.py`。
**`run_id` 绝不复用；一个臂一个全新会话；不得修改 `reportable()`。**
