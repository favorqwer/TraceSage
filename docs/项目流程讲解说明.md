# 三、第一步:反向闭包(取候选边集合)

这一步叫"闭包",意思是:从一个终点事件出发,把所有**可能因果影响到它**的历史活动全部收进来,形成一个封闭的候选集合。收进来之后不做取舍(取舍在后面的阶段),所以这一步决定召回上限。

## 3.1 定位终点事件,算出时间原点

系统拿 POI 的定义去库里查这个事件的所有实例。查到之后取三样东西:

- 涉及哪些进程标识(进程标识的格式是"主机|容器|进程号|启动纳秒",四段合起来才算一个进程,因为同一个进程号会被复用);
- 所有实例里**最早**的开始时刻,它就是**时间原点**。后面提示词里所有时间都是相对这个原点算的秒数,负数表示早于终点事件;
- 所有实例里**最晚**的结束时刻。

如果一条都查不到,系统直接报错停下,不会静默返回空结果。

这些终点事件本身作为"种子"进入闭包,并且**无论后面怎么判,它们永远算已确认**——这是告警事实,不需要判断。

## 3.2 为什么必须能"往回走"

图上一条边的方向是"谁对谁做了什么",不是"谁导致了谁"。要从一个写入动作往回找到"这个文件的内容是谁写进来的",只能沿着**写入侧**反向检索。所以整个闭包是一个**反向遍历**:从终点事件的两个端点出发,不断问"这个顶点的状态是被谁的什么动作造成的",把找到的动作再作为新顶点继续问。

这个过程要满足一条物理约束:**时间不能倒流**。所有往回找的边,其发生时刻必须早于(或等于)当前顶点的门限时刻。

## 3.3 顶点-时间索引:为什么要有、怎么建

如果每往回走一步都去数据库发一次查询,一个有几千万条边的场景会跑成几十分钟。所以系统在第一次运行某个库时,会把**整个库**导成一份本地索引,之后所有闭包取边都读这份索引,运行期间零数据库查询。

索引的构成是四份文件:

- **顶点表**:每个顶点一行,记顶点类别、顶点键、显示内容(进程记可执行路径,文件记路径,网络记端点串),以及进程额外的进程号、名字、命令行、父进程号、网络端点的协议名;
- **邻接记录文件**:每条边存**两条**记录,分别挂在两个端点的块上。每条记录是定长 44 字节,保存两个端点的编号、关系类型码、系统调用码、开始时刻、结束时刻、事件号、字节数、成败码；
- **偏移表**:每个顶点在邻接文件里的起始位置和记录条数;
- **描述文件**:记录格式版本、库名、边总数、最大事件号、顶点数、系统调用码表、构建时间。

构建方式是外部排序:先按端点编号把记录散到 64 个桶文件,再逐桶按"端点编号、开始时刻、事件号"排序后顺序写出。内存占用只跟单个桶的大小同阶,不随库规模增长。

**写入是可中断不损坏的**:开建第一件事是把描述文件删掉;所有数据文件先写成同目录的临时文件,再逐个原子改名;最后才写描述文件当成"提交"。所以任何一步中断,下一次运行只会看到"没有索引"然后重建,不会读到半成品。

**失效判据只有一条**:库的边总数和最大事件号任一变化就重建。索引里不存任何规则判定结果,所以改规则库、改提示词、改参数都不需要重建索引。

## 3.4 三类顶点各自往回取什么边

这是闭包的语义核心,分三种情况:

**进程顶点。** 取它**全部入射事件**,不区分关系类型。具体是:它作为归属进程的所有边(它写过什么文件、连过什么网络、派生过什么子进程),以及"它是子进程"那条派生边。注意派生边在图里两端都是进程顶点,所以在父进程的块里有一条"我启动过谁",在子进程的块里有一条"我被谁启动",两条都取。

之所以两个方向都取,是因为派生关系里"同一主体派生出去的**其它**子进程"也算上游——这是一个有意识的**超集**口径,宁可变多不可变少。

**文件顶点和网络端点顶点。** **只取写入侧**,也就是"进程写文件"和"进程写网络"两类。完全不取读取侧。原因很直接:读一个文件不会把内容送进这个文件,它只说明"有人读了它",不构成这个文件当前内容的成因。读取侧在后面的前向补链里单独处理。

**派生边(p2p)。** 除了把归属进程推入待考察清单,还把"另一端进程"也推入。这就是上面说的超集口径:同一主体派生出去的所有兄弟进程都算可能影响。

## 3.5 时间门限怎么收紧

每个进入待考察清单的顶点带一个**门限时刻**,意思是"只找开始时刻落在这个时刻之前的边"。门限的来源就是发现它的那条边的开始时刻。

同一个顶点可能被多次推入,门限取**最大的那个**。系统额外记一份"这个顶点已经按哪个门限展开过",如果一个新门限不高于已展开过的门限,这个顶点连清单都不进;如果更高,就**重新展开一次**(只补 (旧门限, 新门限] 这段,不是全量重来)。

**进程通道的门限有一个下限:终点事件时刻。** 也就是说进程顶点往回找时,上界被抬到终点事件发生的时刻。理由是同一个进程在终点事件之前的所有活动都可能影响它,不该因为某条边的时刻较早而截断。文件和网络顶点没有这个下限。

待考察清单按门限**从高到低**处理,同门限按顶点类别和顶点键排序。这个顺序只影响处理次序和"同一条边被两个顶点同时找到时记哪一份来源",不影响最终收哪些边。

## 3.6 取数期的两个判据

判据写在 `provenance/config/closure_rules.json` 里,是一张表,一行一条,先命中先赢。它有两个输入类别:

**对象类判据**(看文件路径或网络端点串):

- `/proc/` 下按进程号现生成的伪文件、`/proc/` 其余、`/sys/`、`/dev/`、`/run/` `/var/run/` `/var/lock/`、`unix:[/run/` 这些 → 声明 `no_expand`。
- `no_expand` 的含义是:**从这类对象读出的边照收进闭包,但不沿这个对象往回找写入者**。也就是"边要,上溯不要"。因为这些对象是内核或运行时现生成的,往回找写入者没有物理意义。
- `/dev/shm/`、`/dev/pts/`、`/dev/tty`、`/dev/std`、`/dev/fd/`、用户运行目录下的套接字、容器运行时控制套接字(docker.sock、containerd)→ **不声明任何后果**,也就是正常往回找。这是有意的:`/dev/shm` 是可写内存文件系统,攻击载荷经常落地在那里。
- 命不中任何条目的对象走默认:普通交付对象,正常展开。

**事件类判据**(看关系类型 + 系统调用 + 字节数):

- `f2p`/`n2p` 的 `read`/`recvfrom` 且字节数为 0 → `no_expand`。零字节读说明什么也没读到(通常是读到文件结尾),这条边照收,但不展开。
- `p2f`/`p2n` 的 `connect`/`bind` → `not_delivery`。含义是**这类事件不表示把内容写进对象**,从对象侧取边时不取它;但从进程侧取边时照取(因为它确实是这个进程的历史动作)。

两个判据的分工:对象类回答"这个对象要不要继续往上追",事件类回答"这次操作是不是真的把内容写进去了"。

## 3.7 父进程通道

除了沿图上的边往回走,系统还走一条**不在边上的通道**:进程顶点上记录的父进程号(ppid)。

展开一个进程时,系统按它记录的父进程号,在**同一个容器**里、出生时刻不晚于子进程的进程中,找最近的那一个当父进程,把它推入待考察清单,门限取子进程的出生时刻。

关键点:**这条通道不新增任何边**。父进程的边本来就是图里的真实边,这条通道只是让系统更快地够到父进程。容器进程的父进程号属于宿主命名空间,这一版不处理。

## 3.8 前向补链(在反向闭包之外补一段)

反向闭包有一个结构性缺口:如果攻击链是"A 进程写下一个脚本 → B 进程后来执行它",而 B 进程与终点事件之间没有反向连通的边,反过来走就够不到 B。

所以反向闭包跑完之后,系统再做一次受限的前向探测:

1. 在已收的边里,找出所有**被写入且字节数大于 0 的常规磁盘文件**。排除 `unix:`、`pipe:`、`/dev/`、`/proc/`、`/sys/` 开头的那些,因为它们不是能被别的进程后来读取的常规文件。
2. 对每个这样的文件,查它在"被写入的最早时刻"到"终点事件时刻"之间,被**哪些闭包外的进程读走过**。
3. 如果外部读取者不超过 10 个进程,直接把这些读取事件当追加种子。
4. 如果超过 10 个,逐个进程去看它在这个时间段里的活动里有没有敏感动作(写过对象、派生过进程),有才收。

然后拿"原种子 + 前向种子"**把整个闭包重跑一遍**,而不是增量合并。重跑是为了让跳数、来源等结构上下文保持一致。

## 3.9 闭包产出什么

每条收进闭包的边,除了图上的原始事实(关系类型、系统调用、字节数、开始/结束时刻、事件号、归属进程、两端内容、成败),还额外带四个**结构派生值**:

- **跳数**:这条边离终点事件最少几跳,终点事件本身是 0;
- **来源顶点类别**:这条边是从进程、文件还是网络顶点被回推出来的;
- **来源顶点键**:具体是哪一个顶点;
- **入闭包通道位掩码**:这条边是从哪几类顶点被收进闭包的(多个来源按位或)。这一位后面会用来细分束。

这四个值只用于渲染给模型看和细分束,**不参与任何收边判定**。

**闭包不设任何条数上限。** 上游候选、子进程、管道组成员、待考察清单、单进程边数、查询返回行数全部不设限。理由是:任何条数上限都是按数据分布随机丢边,上限只要小于真实链长就会掉召回,而真实链长事先不知道。

# 四、第二步:把事件折叠成"内容三元组"

闭包产出的是**事件实例**,同一次攻击里"同一进程对同一个文件反复写 500 次"就有 500 条实例。判定和报告都不按实例算,按**内容三元组**算:源内容、系统调用、目标内容。

方向由关系类型决定:进程写文件是"进程 → 文件",文件被进程读是"文件 → 进程",进程派生进程按源到目标。所以 `/usr/bin/mv` 这种"既能当进程又能当文件"的路径不会歧义,因为有关系类型决定谁是源、并附带两端标签。

折叠时同一个三元组聚合成一条记录,记下:

- 实例数;
- 字节数累加;
- 时间范围(最早开始到最晚结束);
- 成败集合(图上返回值小于 0 记失败、大于等于 0 记成功;同一个三元组可能既有成功又有失败,报告按"三元组 × 成败"拆开输出,不去猜哪一条代表它);
- 成员进程集合(同一个三元组可能由多个进程产生);
- 入闭包通道(各实例按位或);
- 两端的**身份集合**:进程记进程标识(完整的四段),文件记路径,网络记四元组。身份和内容是两个概念——"同一个程序跑了 191 次"是 191 个身份、1 个内容;拆开是为了在判定时不把 191 个进程的判定历史混在一起;
- 结构上下文:取所有实例里跳数最小的那一份(相同则保留先到的)。

折叠只合并不删边,**唯一的删除**是:进程在启动期(它首次对外产生写或派生动作之前)读入的、且全图从未被写入过的标准动态共享库(`/lib/` 或 `/usr/lib/` 开头、或路径含 `.so`)。这类边是环境初始化,不承载攻击语义,删掉并计数记入日志。

删这条的理由要说清:它带了"全图未被写入"这个条件,所以不是"所有动态库读取都删",只有**没被篡改过**的才删。

折叠之后,报告和评分的单位就定死了:**内容三元组**。同一条边发生多次只计一次。

# 五、第三步:算出拓扑事实(污染与交付)

判定之前,系统先在候选集合上算出四类客观事实,它们后面被多处复用:

1. **被写过的对象集合**:`write`、`create`、`mkdir`、`rename`、`chmod`、`unlink`、`symlink` 的目标路径(排除 `/proc/`、`/sys/`、`pipe:`);`rename` 和 `symlink` 的**源**路径也算被写过(因为那是被移动/被指向的对象)。
2. **有外发交付的进程集合**:执行过 `write`/`sendto`/`connect` 且目标是网络端点或管道的进程;以及执行过 `clone`/`fork`/`execve` 的进程(派生本身就是一种"向外产生动作")。
3. **入站进程集合**:`accept`/`recvfrom` 且源是网络端点的那些边涉及的进程。这是"会话是由外部发起的"的客观标志。
4. **被污染进程集合**:这是一个**不动点迭代**,最多 30 轮。传播规则三条:
   - 已污染进程写文件 → 这个文件进入"网络落地对象"集合(排除 `/proc/`、`/dev/` 开头);
   - 派生事件的源是"被写过的对象"或"网络落地对象" → 派生出来的子进程被污染;
   - 派生事件的源或归属进程在"入站进程集合"里 → 派生出来的子进程被污染(但如果派生的目标在 `/lib/` `/usr/lib/` `/usr/share/` 下,或名字是 sshd/systemd/dbus-daemon/rsyslogd,就不污染——这些是共享守护进程的正常会话桥接);
   - 派生事件的源或归属进程已被污染 → 子进程也被污染。

这一组事实的用途是区分"例行系统读取"和"受污染主体读取",后面初筛、剪枝、规则匹配准入都用它。

另外系统还会算一组**进程标识变体**:完整四段标识,以及去掉启动纳秒的三段前缀。图上不同来源的字段有时只给三段,两个变体都算同一个进程。

# 六、第四步:静态只读初筛

这是一个纯静态、只读、无模型的过滤,把所有候选边分成两堆。

判据三条同时成立才移出:

1. 系统调用是 `read`;
2. 源路径以这些前缀开头:`/proc/`、`/sys/`、`/lib/`、`/usr/lib/`、`/usr/share/`、`/etc/ld.so.`、`/etc/locale`、`/usr/include/`、`/dev/urandom`、`/dev/null`;
3. 这个对象在全图**从未被写入过**(用第五步算出的污染事实判断)。

命中的边移到"背景"这一堆,理由是"系统只读静态资源且无前序写入污染"。**注意这不是排除,是移到未排除。** 边一条都不会从结果里消失。

**锚点边不参与初筛。** 进入初筛之前,系统已经把锚点(终点事件)那几条边摘出去了,它们直接进已确认集合。

# 七、第五步:符号规则匹配(角色编码 + 攻击基模)

这一步在模型判定之前跑,但它**不决定确认**,只负责给束生成"规则证据卡"。理解它需要先理解两个概念。

## 7.1 角色编码:把顶点写成结构特征串

系统不用"这个文件是不是敏感文件""这个进程是不是可疑程序"这种标签,而是用**结构属性**拼成一个定长字符串,三类顶点各一套格式。

**进程:五段。** 格式是 `P.网络方向.派生形态.实例档.权限档`。

- 网络方向:在它身上出现过 `accept` 就是"入站",出现过 `connect`/`sendto`/`send` 就是"出站",两者都有是"双向",都没有是"无";
- 派生形态:既有 `clone` 又有 `execve` 是"多次派生",只有 `execve` 是"执行",只有 `clone` 是"派生",都没有是"叶子";
- 实例档:以"主机|容器|可执行内容"为键,数这个程序在这个候选集合里出现了几个不同进程实例,按中位数和 95 分位切成"单次/少量/多次"三档;
- 权限档:出现过 `chmod`/`chown` 就是"改过权限",否则是"无"。

**文件:五段。** 格式是 `F.关系位串.写入者档.敏感档.位置档`。

- 关系位串:作为目标被写过是 `w`,被执行过是 `x`,被读过是 `r`,作为源或目标被 `unlink` 过是 `d`,按这四位的组合拼接,全无为 `-`;
- 写入者档:写到这个路径的不同进程实例数,按两档切分成"无/单个/多个"——注意 0 才落"无",1 落"单个";
- 敏感档:路径含 `/etc/shadow`、`/etc/gshadow`、`/etc/passwd`、`/etc/sudoers`、`authorized_keys`、`/.ssh/`、`/etc/ssh/ssh_host` 之一是"认证",以 `/etc/` 开头是"配置",都不是是"无";
- 位置档:落在 `/usr/`、`/lib/`、`/lib64/`、`/bin/`、`/sbin/`、`/boot/`、`/opt/`、`/etc/`、`/var/lib/` 下是"系统",否则是"用户"。

**网络:三段。** 格式是 `N.方向.对端档`。作为 `accept` 的源是"监听",作为 `connect`/`sendto` 的目标是"拨打",两者都有是"双向";对端 IP 数超过档位分界是"多对端"。

**关键点:这些档位的数值分界(实例数、写入者数、对端数)不是硬编码的,是建库时从训练数据算出来写进规则库的,在线按同一组分界映射。** 这样离线和在线对同一个顶点算出完全相同的角色串,规则才能对得上。

## 7.2 基模(Motif):离线挖出来的攻击形态

一个基模是"1 跳或 2 跳的角色链":

- 1 跳基模 = 一个系统调用 + 源角色 + 目标角色;
- 2 跳基模 = 两个跳首尾相接形成链,每个跳有自己的系统调用和角色,外加一个时间约束(第 1 跳的开始不能晚于第 2 跳的结束,也就是说不能倒着发生)。

基模是从训练场景的标准答案里挖出来的,详见第十五部分。

## 7.3 在线匹配怎么进行

对候选集合里的每条边,取它的源角色、系统调用、目标角色,去已准入的基模里找:

- **1 跳**:系统调用相同,且源角色、目标角色都相同;
- **2 跳**:第 1 跳的系统调用和源角色相同、中间角色对得上,然后从中间顶点出发找一条第 2 跳系统调用和第 3 角色对得上的边,且时间不倒序。命中时**两条边都算命中**。

两条**准入前置条件**先卡一遍:

- `login_skip`:边的任一端落在登录机制相关路径下(`/etc/update-motd.d`、`/usr/lib/update-notifier`、`/usr/lib/ubuntu-release-upgrader`、`/snap/snapd-desktop-integration`、`/etc/profile.d`、`/etc/default`、`/var/run/motd`)就跳过。这些是发行版自带脚本,不参与匹配;
- `taint_ok`:边的归属进程或源顶点必须是"被污染进程"或"入站进程"。纯粹的例行系统动作不进入匹配。

命中结果按边记下"这条边命中了哪个基模",并向下传递一个高置信进程集合(命中边的所有端点标识变体)。这个集合目前只作为统计,不影响来路。

## 7.4 这一步的地位

**必须说清:符号匹配的结果不改变任何边的来路。** 它只做两件事:

1. 给每条边记下它命中的基模,供后面的证据卡检索;
2. 供离线蒸馏评测使用。

确认、排除、保留这三段的划分,全部由后面的模型判定和结构规则决定。历史版本里"规则命中直接确认"的做法已经废弃,理由是规则是"典型形态",它命中说明像,不说明是;它不命中说明不像,不说明不是。

# 八、第六步:束划分与逐级细化(系统的核心)

## 8.1 为什么按"束"判,不按边判

一个中等规模的场景,候选边有几万条。逐条问模型要几万次调用,不可行。但把几万条边一次性丢给模型,模型只能给出宏观判断,不可靠。

所以系统把候选边按结构聚成"束"(bundle):**同一个程序、同一种关系类型、同一种系统调用、同一类对象**上的一批边打成一个束,一个束只问模型一个结论。这样一个场景通常剩几十到一百多个束,几批调用就能问完。

代价是同束的边被"绑在一起"判——如果束里既有攻击边又有例行边,整束判 all 会把例行边误确认,判 none 会把攻击边漏掉。这个问题由**逐级细化**解决。

## 8.2 五级层级

同一个候选集合,系统同时准备五套划分,越往下越细:

- **第 1 级**:程序集合 + 关系类型集合 + 系统调用。这是最粗的划分;
- **第 2 级**:第 1 级再加**入闭包通道**。同样一批"某进程写某文件"的边,有些是从进程顶点回推出来的,有些是从文件顶点回推出来的,这一级把它们分开;
- **第 3 级**:第 2 级再加**对象所在目录**。文件按所在目录归组,网络按两端主机对(不含端口)归组,进程统一归一组;
- **第 4 级**:第 3 级再加**具体对象身份**。同一个目录下不同文件分开;
- **第 5 级**:**单条边**。

这套层级有一条不变式:每一级覆盖的成员集合完全相同,且下一级是上一级的**单调细化**——子束的成员一定包含在父束里,不会凭空多出来。系统在测试里校验这条不变式。

## 8.3 逐级推进的主循环

判定从第 1 级开始,推进方式是一个"下钻队列":

1. 把第 1 级的所有束按风险分数排序,作为初始队列。
2. 对当前队列里的每个束,渲染成提示词、分批投给模型,拿到四选一结论:all(整束属于攻击路径)、none(整束无关)、mixed(混杂)、unknown(信息不足)。
3. 按结论改边状态:
   - **all** → 这个束的所有成员边标记为已确认,并把束里的进程、对象、网络主机对、时间窗沉淀进"已确认状态"(后面判其他束时要用);
   - **none** → 所有成员标记为已排除;
   - **mixed / unknown** → 如果还没到最后一级,把这些成员按**下一级的划分**重新分组,产生子束,推入下一轮的队列;如果已经是最后一级,这些边标记为保留(未排除)。
4. 下一轮只处理上一轮拆出来的子束。最多 5 轮。

**这条设计的效果是:粗判能一次搞定整束相同的,细判能拆开混杂的。** 一个"进程写文件"的束如果整体是攻击行为,第 1 级一次调用就确认了几百条边;如果束里混了例行日志写入和攻击载荷写入,模型给 mixed,系统拆到按目录、再按具体文件,把两类分开。

## 8.4 每批怎么切、怎么限流

- 每批最多 **40 个束**;
- 并发 **12** 个请求(网关实测 20 个并发就限流);
- 每个场景判定调用上限 **60 次**;超出上限没判的束**一律按未排除保留**——失败即展开,不删边;
- 每批最多尝试 **2 次**(首次 + 失败后重发);
- 每个束最多列 **2 条成员样本**。样本只影响"模型看得见几条",不影响束的划分,也不影响最终哪些边被确认(判 all 时整束所有成员都进确认,不是只确认样本)。

## 8.5 提示词里到底给了什么

每个束在提示词里占一行或多行,内容依次是:

1. **任务头**:目标事件的三元组、发生次数、时间原点、"只找可能属于攻击路径的上游活动"这个方向说明、相对时间的正负号含义、"清单之外没有需要判断的边"这个口径声明;
2. **批头共享表**(可选,由 `aggregate` 参数控制):
   - "同类规模"表:本批涉及的每个对象类别下一共有多少个束、中位成员数。束行里给出本束在该类别里按成员数的排名和百分位;
   - "上一级束"表:本批子束是从哪个更大的束拆出来的,带程序、动作、成员数、总字节、对象个数、上一级的判定与理由;
3. **束行**:束编号、程序、动作(关系类型 + 系统调用)、对象目录、成员数;
4. **规模行**:成员数、总字节、不同对象数、同类排名;
5. **上一级引用**:如果这个束是拆出来的,给上一级的编号;
6. **跨束痕迹**(可选,由 `annotate_marks` 控制):如果这个束的对象类别或程序在**已经判为相关的束**里出现过,标一行"这些痕迹与已判相关的活动重合";
7. **命令行**:来自进程节点的原始命令行,最多两条,截断到 140 字;
8. **成员样本边行**:每条样本给出进程标识、两端标签、源内容、系统调用、目标内容、折叠事件数、字节数、相对时间;
9. 如果成员数大于样本数,补一行"还有 N 条成员未列出,样本覆盖不同对象"。

**关于两张共享表的理由,配置文件里写得很明确:把上百条连接、上百兆外发这类聚合事实拆散之后,模型会按"例行会话"整批判无关。** 所以拆到子束时,必须把父级的规模事实带过去,不然子束只剩一两条边,模型失去体量感知。

## 8.6 风险排序

第 1 级的束按一个五元组升序排:

1. 是否涉及网络端点(涉及排前面);
2. 束内最小的跳数(离终点事件越近越前);
3. 是否含写入类边(含写入排前面);
4. 离终点事件的时间间隔(越近越前);
5. 成员数取负(成员多的排前面)。

第 2 级及以后按束键的序列化字符串排序,保证可复现。

排序**只改顺序,不改判定语义,不改闸门**。之所以要排序,是因为有调用上限:先判更可能是攻击的束,上限用完时损失更小。

# 九、第七步:四道结构闸门

闸门是**在模型判定之外**的结构约束,用来修两类确定性错误:模型自相矛盾(同一内容判两次结论翻转),以及模型系统性误杀。

## 9.1 空拆闸门(判定前)

如果某个子束的成员集合与它的父束**完全相同**,说明这次拆分没有产生任何新信息。系统不把它再问一遍模型,直接归入未排除,结论记为"空拆"。

配置文件里写明了这条闸门的来历:同一内容被判两次会出现结论翻转,**一次翻转就丢了 399 条相关边**。这是整套参数里修复方差最大的一条。

## 9.2 扇出闸门(判定前)

拆分产生的**单条边**子束(成员数不超过 1)不问模型,直接归入未排除。

理由是:拆分本身会产生大量只有一条边的子束,逐条问模型既浪费调用又不可靠(单条边没有同类对照)。这些边不判也不丢,留在未排除里。

## 9.3 类一致性闸门(判定后)

如果**同一个对象类别**里已经有束被判为"整束相关",那么同类里判"整束无关"的束降级为"混杂",强制继续往下拆。

理由是:模型在不同批次里对同一类对象给出矛盾结论,它自己看不见。这个闸门用"本批已有的判定"约束"本批的后续判定"。

## 9.4 凭证闸门(判定后)

判"整束无关"的束如果命中下面两种已知误杀模式之一,降级为"混杂":

- **束内全是派生边**(只有 `p2p`,没有写入也没有读取)——这种束在错误排除的束里占 63.6%,在正确排除的束里只占 2.5%;
- **束里的进程已经出现在已确认相关的束里**——在错误排除的束里占 18.2%,正确排除的束里占 2.7%。

这两个比例是从历史数据算出来的,写在配置文件注释里作为依据。**凭证闸门必须与空拆闸门同开**——单独开会把更多"无关"降级为拆分,拆分数量翻倍,实测某场景召回从 52 步掉到 31 步。

## 9.5 叶子规则(判定后)

如果某个束是拆分产生的、成员数不超过 1,且模型给了 mixed 或 unknown,但已经没有更细的级别可拆了,这个结论无意义,直接改记为"单条边无可拆,按未排除留"。

## 9.6 闸门之间的关系

四道闸门全部朝同一个方向:**把结论从"排除"推向"保留"或"继续拆"。** 没有任何一道闸门会把边从保留推向确认或排除。

# 十、第八步:两段证据检索

这是 RAG v2 的核心特征:对一个束,同时检索**两段完全独立**的证据。

## 10.1 规则证据(记作 R1、R2、R3)

**来源**:离线蒸馏得到的规则库,按留一折隔离(测某个场景时只读"不含这个场景"的那一折)。

**检索入口**:不是文本向量,是图查询。对束里**每一条成员边**,用它的源角色、系统调用、目标角色去规则库里查:

- **精确(R2)**:系统调用、源角色、目标角色三项全同;
- **部分(R1)**:系统调用相同,且**至少一个**完整角色相同;
- 精确先查,部分查询时排除已经精确命中的那些,避免重复。

**排序**:先按对齐等级(R2 优先),再按训练折查准率降序,再按攻击命中数降序,最后按编号。

**上限**:每个束最多 3 条。

**卡片字段**:R 编号、基模编号、精确对齐多少条成员 / 部分对齐多少条、训练折查准率、攻击命中 / 背景命中 / 忽略命中、支持场景数,以及这个基模的跳链。

跳链的渲染有一个标记:如果某一跳的系统调用与**这个束**的系统调用一致,这一跳后面标 `[与束系统调用一致]`。这个标记是为了解决一个具体问题:一个 2 跳基模的第 1 跳常常是 `execve`,第 2 跳才是束的系统调用;模型容易默认引用第 1 跳,引用守卫会因此判它无效。

**硬约束:规则卡里不出现任何 ATT&CK 技术编号。** 规则与技术的对应关系只保留在离线知识库里用于评测,不进入检索和提示词。

**空结果**:显示"本束没有规则证据",不生成任何 R 编号。

## 10.2 技术证据(记作 E1、E2、E3)

**来源**:ATT&CK 技术库 + 45 条人工写的行为观测。

**检索入口**:对每条成员边,用系统调用查所有声明了这个系统调用的行为观测,然后判断是否命中。命中分两档:

- **T-强**:行为观测里写了角色模式,且这个角色模式与**成员边**的角色匹配(前缀匹配);这是真正的"这条边符合这个技术的观测条件";
- **T-弱**:只有进程名匹配、或只有路径匹配、或者这条观测本身**只声明了系统调用条件**没有任何其他条件。

这个分档的判据要看清:如果一条观测声明了角色模式但没匹配上,但进程名匹配上了,它**仍然只能是弱**;如果一条观测什么条件都没声明(只有系统调用),它也是弱。只有角色模式匹配上才算强。

**排序**:观测置信度降序,再按命中成员数降序,再按命中条件数降序,最后按技术编号。

**上限**:每个束最多 3 个技术。

**强证据注入提示词,弱证据只写进运行记录**(trace),不注入。

**卡片字段**:E 编号、ATT&CK 编号、技术名称、战术、命中条件、观测置信度、是否人工核验。

**E 编号的含义要说清:E 是"本束内的证据编号",不是 ATT&CK 编号。** ATT&CK 编号形如 T1071,只用于识别技术本身。

**空结果**:显示"本束没有技术证据",不生成 E 编号。

## 10.3 为什么必须严格分开

README 与代码都强调几条不可逾越的规则:

- 规则卡不含 ATT&CK 技术编号;
- 技术卡不含规则编号和跳号;
- 不允许用"技术反查规则"把技术标签包装成规则证据;
- 没有对应证据时不允许编造 R/E 编号。

原因是这两段证据的**认识论地位不同**:规则是"从训练场景里挖出来的历史攻击形态",技术是"MITRE 归纳的行为类别"。如果把技术反查成规则,就等于把"这个行为像某个技术"伪造成"这条边符合某条历史攻击链",评测时无法区分两类证据各自的贡献。

`retrieve_for_edge` 这个接口(带 `technique_entry` 的路径)保留了"从技术入口反查基模"的能力,但**在线主路径不调用它**,主路径只调用 `retrieve_rules` 和 `retrieve_techniques`。

## 10.4 缓存的粒度

规则证据和证据技术的检索结果按一个复合键缓存:源角色、系统调用、目标角色、源标签、目标标签、束内程序列表。同一批次里同一形状的边只查一次库。

# 十一、第九步:引用守卫

模型判 all 时必须给出引用,守卫负责校验引用是否成立。

**只检查 all。** none、mixed、unknown 不检查。

**检查顺序:**

1. **两类证据都没有**:如果模型还写了 R 或 E 编号 → 判定为"无证据却编造引用",降级 mixed,统计计入 `fabricated_citation`;如果没写编号 → 只计一次"无证据"(不降级,因为没证据本来就不要求引用)。
2. **有证据但一个编号都没写** → 降级 mixed,计 `missing_citation`。
3. **引用了规则**:编号必须在规则证据里;`hop` 必须是整数;这一跳必须在这个基模的跳链里真实存在;这一跳的系统调用必须包含束的系统调用;**精确规则要求源角色和目标角色都与同一个成员边一致,部分规则要求至少一个角色一致**。任一不满足 → 降级,分别计入 `bad_rule`、`bad_hop`、`bad_alignment`。
4. **引用了技术**:编号必须在技术证据里,否则降级,计 `bad_technique`。技术没有跳号概念,不检查 hop。

**引用来源有两处**:模型输出的独立字段(`rule_id`、`tech_id`),以及**理由文本里出现的 R/E 编号**(用正则扫)。所以模型在理由里写"R1 符合但…"也会被当作引用。

**统计写进运行日志的 `RAG_GUARD` 行**,并汇总到评测报告。

**这条守卫的作用:** 它把"模型口头声称有证据"变成"模型引用了真实存在的证据编号"。如果模型编造编号,它的 all 结论会被降级,不会污染确认集合。

# 十二、第十步:因果公理补全与纯化

模型判完之后,系统再用一组**操作系统级别的因果公理**做一次补全和纯化。这一步的输入是"已确认集合 + 未排除集合 + 已排除集合"。

各阶段开始时先把模型判为 all 的边合进已确认集合,并过滤掉一个特例:源或目标是 `<NA>`(图上取不到可执行文件)且系统调用是 `execve` 或 `clone` 的边——这类"未知执行体"的粗粒度泛化边不收。

## 12.1 四条补全公理

**公理 A:失陷进程树发起的子命令派生。** 如果一条 `execve` 或 `clone` 边的源端身份里有任何一个进程已经在已确认集合里,且目标是一个绝对路径或相对路径,就把它提升为已确认。提升后把它的成员进程和目标进程也加进已确认进程集合——所以这个推导会**链式传播**:失陷进程派生的子进程再派生,也能推出来。

**公理 B:失陷进程对临时可写空间的载荷落地。** 如果一条 `mkdir`/`chmod`/`write`/`open` 边的源端身份属于已确认进程,且目标是 `/tmp/`、`/var/tmp/`、`/dev/shm/` 之下,提升为已确认,并把这个目标加进"已写文件集合"。

A 和 B 放在一个最多 3 轮的循环里反复执行,直到某一轮没有任何新提升。

**公理 C:写后读(RAW)污染装载。** 如果一条 `read`/`open`/`mmap` 边的源是公理 B 记下的"已写文件集合"里的文件,提升为已确认。这条公理闭合了"落地 → 之后被读取或执行"这条链。

**公理 D:匿名管道双端对齐闭环。** 先在全量候选(未排除 + 已确认)里统计每个管道对象:`pipe:` 作为目标且系统调用是 `write`/`sendto`/`sendmsg`/`ioctl` 的,记下写端进程;`pipe:` 作为源且系统调用是 `read`/`recvfrom`/`recvmsg`/`ioctl` 的,记下读端进程。一个管道**写端和读端都有已确认进程**才算"有效闭环管道"。然后:已确认进程向有效管道写入的边,提升为已确认。

道理是:管道本身没有身份,只有两端都有已确认主体时,这条管道才在攻击链上;只有一端的话,另一端的活动不知道是谁,不能凭管道对象相同就认为连通。

## 12.2 三条纯化规则

补全之后,对已确认集合逐条过纯化,**锚点边直接放行,永不纯化**:

1. **被动内核运行时加载**:系统调用是 `mmap`/`access`/`stat`/`fstat`,且任一端落在 `/etc/ld.so.`、`/etc/localtime`、`/etc/nsswitch.conf`、`/usr/lib/locale/`,或者是 `/lib/` `/usr/lib/` 下含 `.so` 的路径。这些是 Linux 程序启动时内核和动态链接器强制执行的只读加载,不承载攻击语义。移到未排除。
2. **悬空管道**:任一端是 `pipe:` 且这个管道不在有效闭环管道集合里。移到未排除。
3. **无关的系统级后台维护任务**:任一端包含 `unit-root`、`dpkg`、`apt`、`systemd-timedated`、`fstrim`、`update-notifier`、`motd`、`fwupdmgr`、`system-generators` 这些标记。移到未排除。

纯化移出的边**进未排除,不进已排除**。这个区分很重要:已排除是"确认无关",未排除是"判不了"。公理纯化只是说"这条边不符合攻击语义",不说"它是攻击链的一部分但无关",所以放在保留区。

# 十三、第十一步:后置剪枝(碎屑剥离)

这是最后一道过滤,针对四类"确认了但其实是操作碎屑"的边。锚点边同样永不剪。

## 13.1 包管理器内部碎片

如果边的源程序名(取路径最后一段)在包管理器名单里(`dpkg`、`dpkg-deb`、`dpkg-split`、`dpkg-preconfigure`、`mandb`、`ldconfig`、`ldconfig.real`),且目标是内部落点(`.dpkg-new`、`.dpkg-tmp`、`.triggers`、`/usr/share/doc/`、`/usr/share/man/`、`/usr/share/locale/`、`/var/cache/man/`、`/var/cache/apt/`、`/var/lib/apt/lists/`)或者是管道,就剪掉。

另有两条豁免:`execve` 永不剪(执行动作本身有语义);路径里含 `postinst` 的永不剪(那是安装脚本,可能承载真实行为);目标落在锚点所在目录下的永不剪。

`apt-get` 的 `read`/`write` 且目标是 `/var/lib/apt/`、`/var/cache/apt/`、管道,也算碎片。

## 13.2 本地 DNS 伪连接

任一端是回环地址上的 DNS 解析器(53 端口、127.x 或 0.0.x),剪掉。理由是系统内部的存根解析器,不构成对外通信。

## 13.3 死端认证读取

如果一条边是 `read`/`open`/`sendfile`,源路径是认证或配置文件(`/etc/shadow`、`/etc/passwd`、`/etc/sudoers`、`/etc/group`、`/etc/gshadow`、`/etc/subuid`、`/etc/subgid`、`/etc/security/opasswd`、`/etc/pam.d/common-auth`、`/etc/pam.d/sshd`,加 `/etc/nshadow`、`/etc/shadow+`、`/etc/passwd+`),且**同时**下面三条都不成立,就剪掉:

- 读取进程或它的子进程有对外交付(网络外发或高影响写入)。这里有一个传播:沿"父→子"关系把子进程的交付能力传给父进程,做 3 轮;
- 是 sshd 读 authorized_keys 这类会话认证(这是登录机制的正常动作);
- 是会话侦察:读的进程或其父进程属于交互式会话进程(`bash`、`sh`、`sshd`)。

理由是:读认证文件本身不是攻击,读完之后没有把内容送出去、也不是交互式会话里在翻文件,那这次读没有信息流出口。

## 13.4 自派生空转边与管道降噪

- `execve` 且源等于目标且命中的基模是"进程血缘派生" → 剪掉(自己执行自己,空转);
- 管道边:如果管道的写端里有做过网络外发/接收的进程,或名字含 `curl`/`wget`,且读端含 `bash`/`sh`/`python`,或者这条边就是写端 → **保留**(这是"下载后直接管道执行"这种真实攻击形态);否则如果命中特定基模 → 剪掉。

## 13.5 最终三段怎么合并

剪枝之后,系统把最终的三个集合算出来:

**已确认** = 剪枝后剩下的确认集合。

**未排除** = 四个来源合起来:

1. 公理纯化移出的边;
2. 初筛移出的背景边;
3. 碎屑剪枝移出的边;
4. 模型判 mixed/unknown 但最终没进确认集合的剩余歧义边。

**已排除** = 模型判 none 的边里,没有被公理补全重新提升上来的那些。

注意第 4 条的写法:先取"排除后剩余的歧义边",再排除掉已经在确认集合里的。所以一条边即使模型判了 mixed,如果公理补全把它提升了,它也不会重复出现在未排除里。

# 十四、第十二步:报告与评分

## 14.1 报告结构

报告是一个 JSON 文件,四个顶层键:

- `scenario`:场景名;
- `edges`:已确认边的数组;
- `unexcluded`:未排除边的数组;
- `excluded`:已排除边的数组;
- 外加 `stats`(统计)和 `rules_library`(规则库元信息)。

每条边记录源内容、系统调用、目标内容、两端标签、实例数、字节数、成败集合、时间范围、关系类型集合、成员进程、两端身份、跳数、来源顶点、通道位、事件号列表,以及来路(`origin`)和理由(`reason`)。

**端点口径有一条硬规则**:进程端点在图上取不到可执行文件时,报告里写 `<NA>`,不写进程主键。而且报告端点内容**不能是进程主键**——如果拼出来的内容是四段格式的进程标识,直接抛错。这条是为了防止"把进程标识当程序名"这种报告污染。

## 14.2 评分口径

评分工具是仓库根的 `tools/score_report_product.py`(不在 provenance 包内,跨组件共用)。

- **召回按步骤算**:标准答案里的一条"攻击步骤"只要在报告的已确认边里出现,就算命中;
- **查准按边算**:报告里每一条已确认边,如果它在标准答案里,算正确;
- **同一条边多次发生只计一次**。

所以召回的分子是"命中的步骤数",分母是"标准答案步骤总数";查准的分子是"正确边数",分母是"报告的三元组数"。

## 14.3 正式基线

正式基线由 `tools/promote_v2_baseline.py` 生成,包含 10 份压缩报告、一份汇总、一份总览和代码指纹。当前口径是 **77.37% 召回、59.66% 查准**(701/906 步,19540/32751 条边,221 次调用)。README 明确标注这是**单次运行**,没有重复运行,波动范围未知。

# 十五、离线部分:规则库是怎么来的

在线部分用的规则证据不是手工写的,是从训练场景离线挖出来的。这一步不在运行时路径上,但决定了规则证据的质量。

## 15.1 挖什么

1. **按留一折分组建训练集合。** 测场景 k 时,训练集合是除 k 之外的其余场景。
2. **对每个训练场景跑一次"轻量闭包"**:只取边的关键字段,不算拓扑事实、不算规则、不做判定。这样得到每个训练场景的候选边集合。
3. **用标准答案给候选边打标签**:每条边分三类——攻击边(在标准答案里)、背景边(不在答案里且属于静态只读背景)、忽略边。这三类计数就是后面规则卡上的"攻击/背景/忽略命中"。
4. **频繁子图挖掘**:在同一个候选集合里统计"系统调用 + 源角色 + 目标角色"这种 1 跳形态的出现次数,以及两条首尾相接的 2 跳形态的出现次数。达到支撑度门槛的形态成为候选基模。
5. **给每个基模算一个规范拓扑指纹**,由指纹派生稳定编号(哈希前 12 位)。同一指纹只出现一次,和挖掘顺序、来源场景无关。

## 15.2 准入:贪心选,不用阈值

候选基模要经过一次"准入"筛选才进折库。判据里**不含任何数值阈值**:

- **选谁**:算每个形态的**边际查准率** = 它新带来的攻击边数 / 它新带来的报告边数,选最高的;
- **平局**:按拓扑指纹升序;
- **何时停**:没有任何形态能带来新的攻击边就停。

准入结果写进折库的 `selected` 名单。在线加载折库时,只有 `selected` 里的基模参与匹配——这就是 `is_motif_admitted` 的全部内容,它不读任何置信度阈值。

## 15.3 折库内容

每个场景一份折库 JSON,里面有:

- `motifs`:全部候选基模;
- `selected`:准入名单;
- `train_scenarios`:训练场景列表(必须不含被测试场景);
- `test_scenario`:这份折库是为哪个场景准备的;
- `role_cuts`:角色档位分界(离线在线共用);
- `greedy_trace`:准入过程的轨迹;
- `stats`:统计;
- `fingerprint`:指纹。

**在线加载时有三条校验**:文件必须存在;`test_scenario` 必须等于当前场景;`train_scenarios` 里**绝不能出现**当前场景。任何一条不满足就报错。这是折隔离的硬保证——如果折库混进了测试场景自己的答案,所有评测数字都作废。

## 15.4 规则知识图谱(可选,给证据检索用)

规则检索是通过 Neo4j 里的一个独立库(`trace-rules-kg-v1`)做的,不是读折库文件。这个库的结构:

- **全局节点**:867 个 ATT&CK 技术、15 个战术、45 个人工行为观测;
- **按折节点**:10 折合计 1,454 个基模、2,362 个跳、90 个案例;
- **关系**:基模含跳、跳接跳、基模实现技术、基模源自案例、技术属于战术、行为观测观察技术。

**折隔离在这个库里同样成立**:测场景 k 时,规则检索只读第 k 折的基模/跳/案例节点;技术、战术、行为观测是**全局知识**,不按折隔离。

构建链路是:`run_loo_folds.py` 产出折库 → `build_rule_kg.py` 从折库构建 JSON → `build_rule_kg_neo4j.py` 写入 Neo4j;技术侧由 `build_attack_kg.py` 从 ATT&CK 快照和 45 条行为观测构建。

## 15.5 蒸馏代码的两个作用

`rules/offline.py` 等离线代码除了挖规则,还在准入时复用**与在线完全相同的匹配谓词**(`rules.online.MatchIndex`)。也就是说,离线算"这条边命中这个基模"和在线算"这条边命中这个基模"用的是同一份代码,保证两端一致。

# 十六、几个关键设计取舍

**1. 上游不设条数上限。** 所有上限都在判定侧(批大小、调用上限、样本数),取数侧一个都没有。理由是上限一旦小于真实链长就静默丢边,而链长事先不知道。代价是内存和耗时,换来的是召回上限不被自己砍掉。

**2. 删边只有一处。** 整个流程里唯一"从结果中消失"的操作是折叠时丢掉启动期未被篡改的动态库读取。其余所有过滤——初筛、公理纯化、碎屑剪枝——移出的一律进"未排除",不进"已排除"。这个设计让"排除"这个动作只在模型明确判 none 时发生,可审计。

**3. 判定单位是束,不是边。** 这是为了调用预算。代价是引入"整束绑定"误差,由五级细化和四道闸门缓解。系统自己承认这个代价:README 明确写着"证据是束级,不是边级;没有逐边证据卡、逐边引用和引用忠实度测量"。

**4. 失败即展开。** 调用超上限、模型没给结论、模型给了越界编号——所有异常路径都落到"保留"。系统不把"没判"当成"无关"。

**5. 规则不决定确认。** 符号匹配只产证据卡,来路由模型判定 + 结构规则决定。这条是与历史版本最大的区别,也是为了不让规则的覆盖范围变成系统的召回上限。

**6. 结构闸门全部单向。** 四道闸门只会把"排除"推回"保留"或"继续拆",没有一道会把边推向确认。这样闸门不会制造假阳性,只会减少假阴性。

**7. 参数全部外置。** 并发数、批大小、样本数、调用上限、四道闸门的开关、剪枝名单、理由长度、重试策略,全在 `provenance/config/navigator.toml` 里,代码不写数字。配置文件里逐条写了取值依据(比如"网关实测 20 个并发就限流,取 12 留余量""开 thinking 后判定耗时从 74.6 秒涨到 231.1 秒")。
